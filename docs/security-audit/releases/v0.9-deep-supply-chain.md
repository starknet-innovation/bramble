# v0.9 deep audit — release build provenance

Follow-up to the [v0.9 deep adversarial audit](../v0.9-deep/), covering one supply-chain defect an
external review substantiated against the hotfix branch. Method, severity definitions, and residual
boundaries are defined in the [parent document](../v0.9-deep/). The finding pre-dates the branch and
is present on `main`; it is recorded here because the branch added artifact-provenance gates around
a build step that stayed outside their envelope.

It is `EXT-H02` in the [v0.9.1 external security review](../v0.9-external-review/), which carries
the other thirteen findings from the same review. It was delivered privately; because it is
Resolved, the defect and the remediation are recorded here and the reviewer's reproduction material
is not.

### EXT-H02 — vendoring executed code that no pin covered {#ext-h02}

- **Severity:** High  |  **Area:** release provenance  |  **Status:** Resolved
- **Location:** `scripts/vendor-privacy-sdk.ts`

**Mechanism.** `bun run vendor:privacy` checked the privacy SDK out at a pinned commit and then
handed the browser-bundle build to an upstream package script. A package script is only pinned in
the sense that the pinned commit fixes its text; the text itself asked a registry for an executable
by bare name at build time. That executable ran with the release workspace's write access, and it
ran *before* `check:privacy`, `bun run check`, `bun run build`, and `bun run package:extension`.

**Impact.** Every provenance gate in the release path verifies bytes that already exist: artifact
digests, the vendored checkout's commit and worktree status, the extension manifest, and the package
checksum. Code that executes ahead of all of them can edit wallet source, the gates themselves, or
the packaging scripts, and still leave every expected digest matching. A matching bundle digest
therefore proved the bundle, not the artifact built beside it.

**Remediation (shipped).**

- `scripts/vendor-privacy-sdk.ts` no longer runs any upstream package script. After
  `npm ci --ignore-scripts` installs the lockfile graph exactly, it executes the pinned upstream
  build source with the Bun binary already running the vendoring step, against the esbuild release
  the upstream lockfile records with an integrity hash. The installed build-tool version must equal
  the locked one — including the platform binary esbuild spawns — or vendoring throws before
  building. Bun's runtime auto-install is disabled, so an import the lockfile does not cover fails
  the build instead of fetching a package mid-compile.
- The upstream build receives a minimal environment (no registry tokens, no CI credentials) and the
  wallet checkout's porcelain status is captured either side of it, so a build that reaches out of
  its own directory is refused rather than blessed by the digests that follow.
- `scripts/check-privacy-sdk.ts` now re-derives *how* the bundle came to exist, not only what it
  hashes to: it refuses a vendoring step that resolves an executable by name or delegates to an
  upstream package script, and re-verifies the locked build tools from the checkout. `bun run build`
  reruns this gate before copying the bundle into the extension.
- `scripts/workflow-security-policy.ts` refuses build-time executable resolution — package runners,
  `dlx`, unlocked installs, or a downloaded script piped into a shell — in any workflow that vendors
  a pinned source, i.e. every workflow on the release-artifact path.
- `tests/scripts/vendor-execution-policy.test.ts` is the durable part. It derives the vendor-script
  list from `package.json`'s `vendor:*` entries rather than a hand-written table, resolves the
  package scripts a vendoring step would delegate to, and fails on build-time name resolution or on
  a build tool absent from the relevant lockfile. Pinning one tool removes one instance; this
  removes the class.

**Verified offline.** The pinned upstream bundle and source map rebuild byte for byte under the
locked runner — both digests in `scripts/check-privacy-sdk.ts` reproduce from a deleted output
directory, under the minimal environment, with auto-install disabled. `check:privacy` rejects a
vendoring step that reintroduces the delegation, and the new conformance tests fail against the
pre-fix script.

**Residual.** Two of the reviewer's preferences remain open and are tracked rather than claimed:
the upstream build still executes inside the wallet checkout (containment is detected after the
fact, not prevented by an isolated workspace), and the release package is still constructed in the
same workspace that ran the upstream build rather than in a fresh trusted checkout. Both are
workflow-topology changes to the self-hosted release runner and are scoped separately.
