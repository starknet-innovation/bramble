# v0.9 deep audit — high and medium findings

Continuation of the [v0.9 deep adversarial audit](../v0.9-deep/). Method, verification, and
residual boundaries are defined in the parent document.

### MCW-V09-101

- **Severity:** High  |  **Area:** crypto  |  **Status:** Resolved
- **Location:** `src/starknet/typed-data.ts:39`

**Mechanism.** typedDataHash (src/starknet/typed-data.ts:33-50) passes the payload straight to starknet@10.0.2
snip12.getMessageHash with no revision policy, and isTypedDataShape (typed-data.ts:18-28) validates
only the four-key envelope plus a JSON budget — it never inspects a single entry of `types`. `rg -n
"revision|StarkNetDomain" src/` returns zero hits outside Ledger target-ID code. starknet's
identifyRevision selects LEGACY (revision 0) whenever `types` contains a `StarkNetDomain` key and
`domain.revision` is absent.

**Impact.** Violates threat-model objective 3 — "the side panel shows the user the same transaction, typed data,
chain, fees, and account that will be signed." A connected site obtains a user signature over the
message hash of an arbitrary third-party SNIP-12 struct while the approval card renders a flat,
benign-looking payload.

**Remediation.** Reject SNIP-12 revision 0 in typed-data.ts: require `domain.revision === "1"` together with a
`StarknetDomain` entry. Independently — because revision 1 is injectable the same way through field
names, whose escaping wraps in quotes without escaping inner quotes — reject any type name or field
name in `types` containing `(`, `)`, `,`, `:` or `"`, and reject any field `type` that is neither a
declared type, a declared type with …

**Resolution note (revision 0).** The recommended revision-0 ban was not adopted, because it is not
what closes the finding and it breaks deployed dapps. The forgery is a *name* problem: `encodeType`
builds one flat string whose only structural characters are `(`, `)`, `,`, `:` (plus `"` on revision
1), and neither revision escapes them inside a name. A deny-by-default grammar that admits no
separator and no non-ASCII code point — applied to every type name, field name, field type and tuple
element — makes that string parse back to exactly one graph, on either revision. Revision 0 is
additionally validated against its *own* vocabulary — no presets, no enums, no tuples — because its
`encodeValue` coerces anything it cannot resolve to a felt, which is the primitive the forgery is
built from; and revision identification now mirrors the pinned library's `identifyRevision` exactly,
including a numeric `1` (which the library accepts) and a numeric `0` (which it does not).

**Resolution note (constructs the grammar does not reach).** Two SNIP-12 constructs keep their shape
out of `encodeType` entirely, so the grammar alone does not make them injective and each needed its
own rule.

- `merkletree` omits its `contains` leaf type from the encoding. With a basic-type leaf the leaf hash
  *is* the felt the site supplied, so a payload declaring `contains: "felt"` and pasting another
  struct's leaf hashes into `message` reaches the honest payload's root: two structures, one
  signature, verified by execution on both revisions. A leaf must therefore name a declared struct or
  a revision preset; both hash as `H(typeHash, …values)`, which turns the substitution into a hash
  preimage. This closes the ambiguity — an earlier note in this file claimed no validator at this
  boundary could separate the two, which was wrong, and also credited the approval card with
  rendering the declared leaf type, which it does not do.
- An `enum` field encodes as `"f":"Variants"`, indistinguishable from a plain reference to the same
  type. Variant lists and ordinary structs are now disjoint by shape: a type named by some enum's
  `contains` must be non-empty, hold only tuple payloads, and be reachable only through that enum
  field (never as a field type, array element, merkle leaf, primary type, or domain struct), while
  no other type may hold a tuple at all.

**Verification.** `tests/starknet/typed-data-injectivity.test.ts` executes the claim instead of
arguing it. It generates grammar-conforming graphs across the whole accepted vocabulary — nested
structs, arrays, presets, tuples, enums and merkle trees — keeps the ones the wallet accepts, and
asserts that no two structurally distinct graphs share an `encodeType` string (outside `merkletree`,
whose leaf type is deliberately not part of the encoding) and that no two share a full message hash
(everywhere, `merkletree` included). It asserts the corpus actually contains enum, preset and merkle
graphs, so the sweep cannot quietly narrow, and it first replays both known collision pairs — the
separator forgery and the merkle-leaf substitution — to show the search flags them.

**Known and accepted.** A payload may declare a type nothing references — most commonly the other
domain spelling, which back-compat payloads carry deliberately — and that declaration changes no
hash. Two payloads differing only in such a declaration therefore share a message hash. This is not
a display ambiguity: the approval card walks outward from `primaryType` and the revision's own domain
struct, so an unreferenced declaration renders nothing at all. Refusing unreachable declarations
would break the common both-spellings payload for no gain, and the sweep above generates only fully
reachable graphs for the same reason.

### MCW-V09-102

- **Severity:** High  |  **Area:** origin-trust  |  **Status:** Resolved
- **Location:** `src/starknet/multisig.ts:361`

**Mechanism.** computeMultisigTransactionId (src/starknet/multisig.ts:361-376) obtains the proposal id by asking
the node to evaluate the contract's `hash_transaction` view and returns `feltAt(response, 0)` with
no local recomputation and no cross-endpoint agreement — withRpcFallback
(src/starknet/provider.ts:215-232) returns the first endpoint that answers, and only transport-level
failures fail over.

**Impact.** The wallet displays the proposal the user created — summary, target, entrypoint, calldata, salt —
while the confirmation it signs adds quorum to a different on-chain proposal chosen by whoever
controls the RPC answer. In a multisig the co-signer is precisely the adversary quorum exists to
contain, so an attacker who is one signer and can influence the victim's endpoint harvests the
victim's confirmation onto the attacker's own proposal and reaches quorum.

**Remediation (shipped).** The id the wallet uses is the one it derives. `multisigTransactionId`
(`src/starknet/multisig.ts`) mirrors OpenZeppelin MultisigComponent v3.0.0's `hash_transaction_batch`
exactly — a Pedersen chain from 0 over the batch length, then the call's `to`, selector, calldata
length and calldata felts, then the salt — and `computeMultisigTransactionId` reads the contract's
`hash_transaction` view purely as a cross-check, throwing on any disagreement so no id the wallet did
not compute can be stored, confirmed, or signed against. A record keeps its id and its call as separate
fields, so `multisigCallMatchesId` re-derives the binding before any `execute` invoke is built from a
stored proposal, including one written by an earlier version; it is total, so a malformed call, salt,
or id is a plain refusal.

**Verification.** `tests/starknet/multisig-proposal-id-binding.test.ts` pins the derivation against a
vector produced by the pinned `openzeppelin_governance` 3.0.0 sources themselves — ground truth, not a
self-derived expectation, which matters because a self-consistent chain mirroring the wrong spec would
pass its own tests — and pins that a node substituting any other id, including an off-by-one-bit one,
fails the read closed. `tests/background/multisig-stored-proposal-id-binding.test.ts` pins the stored
half.

### MCW-V09-103

- **Severity:** Medium  |  **Area:** origin-trust  |  **Status:** Resolved
- **Location:** `src/background/swap-ops.ts:131`

**Mechanism.** buildPolicyError (src/background/swap-ops.ts:148-171) is the only local gate on the untrusted AVNU
build response before the bundle is frozen. It enforces exactly three things: at most 4 calls, at
most 1 approve, and — via approvalCallPolicyError — that an approve targets the sell token for
exactly the sell amount. approvalCallPolicyError opens with `if
(!APPROVE_ENTRYPOINTS.has(call.entrypoint)) { return null; }` (swap-ops.ts:131-133), so EVERY non-
approve call is unconditionally accepted regardless of target contract, entrypoint, or calldata.

**Impact.** A compromised AVNU API — a named in-scope adversary ("adversarial ... swap ... responses", threat-
model.md:37) — can substitute a bare `transfer(attacker, 2**256-1)` on the user's tracked sell token
for the swap route. This is not bounded by any allowance: the account contract executes it directly,
draining the entire balance of that token in one transaction the user believes is a small swap.

**Remediation (shipped).** The counterparty is allowlisted, not just the amount. The AVNU router is
pinned per network in `src/starknet/avnu.ts` and the approve spender must `sameFelt` it; the
non-approve early return is replaced by a positive allowlist — every remaining call must run on that
same pinned router through one of its pinned swap entry points (`isAvnuSwapEntrypoint`), so both the
counterparty and the selector are wallet-chosen and never inferred from the response. A negative rule
would not have been a description of a swap: it admits `set_approval_for_all`, `burn`, `upgrade`, and
is evadable by calldata arity alone. The approval itself must be exactly one call, on the sell token,
for exactly the quoted amount, read through the shared uint256 join so a `(0, huge)` limb spelling
cannot slip past; the "no decoded transfer" rule is kept behind the allowlist as defence in depth; and
an admitted build carrying more swap calls than the one reviewed is flagged on the receipt rather than
listed silently. The residual is stated rather than glossed: the route's own calldata still belongs to
the aggregator, so a tampered build can cost up to the exact allowance the user reviewed — and nothing
else the account holds. `tests/background/swap-build-policy.test.ts` drives fifteen builds through the
real handler, including that the pinned mainnet address is AVNU's published exchange contract.

### MCW-V09-104

- **Severity:** Medium  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/sidepanel/sign-request.ts:97`

**Mechanism.** signRequestDetails is type-directed for exactly one level and one section. Top-level message rows
use the declared field list (sign-request.ts:95,100) — correct. But the domain block is built from
`rows(Object.entries(domain))` (sign-request.ts:97) and is never intersected with
`types.StarkNetDomain` / `types.StarknetDomain`, and nested values are rendered with
`JSON.stringify(value)` in valueText (sign-request.ts:59-67) rather than via the nested struct's
declared fields.

**Impact.** The approval card can be made to state facts the signature does not commit to. Most importantly
`chainId`: an attacker displays `chainId: SN_SEPOLIA` while producing a domain hash with no chain
scoping whatsoever — exactly the field a cautious user checks, and exactly the reason a user
switching to testnet before interacting with an unfamiliar site gains no protection.

**Remediation (shipped).** The card is type-directed at every level.
`packages/presentation/wallet-ui/src/sidepanel/shared/sign-request-decode.ts` resolves the revision
through the shared `snip12Vocabulary` — the same description the hashing gate works from, so the
card and the hash can never disagree about which domain struct applies — derives the domain rows
from that struct's declared field list, and recurses into nested structs, arrays, presets, enums,
and merkle leaves using their declared fields. Anything present in the data but absent from the
declarations lands in a separate block headed "shown by the site but NOT signed", styled distinctly
and bounded in height and row count so a site cannot scroll its own warning off screen. Section
labels are fixed strings, never interpolated from `primaryType`, or a site-chosen type name would
reproduce the banner verbatim over the signed block.

Two things beyond the finding's wording were needed to make that honest. A value the decoder cannot
place at all is not rendered as either kind: the view reports `classified: false` and
`src/sidepanel/approval-cards.ts` withholds the approve control entirely, showing a deny-only row
and `SIGN_REQUEST_UNCLASSIFIED_WARNING`, so the card and the affordance can never disagree about
whether signing is on offer. And the hashing gate closed the same hole from the other side: an
undeclared domain key is now refused outright by `isTypedDataShape`, so the displayed-but-unhashed
`chainId` cannot even reach a signature.
`packages/presentation/wallet-ui/tests/sidepanel/journeys/approvals/sign-request-display-integrity.test.ts`,
`sign-request-unhashed-domain.test.ts`, `sign-request-unhashed-nested.test.ts`,
`sign-request-merkle-order.test.ts`, and `sign-request-classification.test.ts` pin the rendering.

### MCW-V09-105

- **Severity:** Medium  |  **Area:** plaintext-lifetime  |  **Status:** Resolved
- **Location:** `src/background/provider-ops.ts:180`

**Mechanism.** src/background/session.ts:38-42 states the contract explicitly: "`getPassphrase` renews the
inactivity window and is for user-initiated operations; `peekPassphrase` reads without renewing and
is for passive paths (status polling, event re-queries) so they can never hold the wallet unlocked
forever." getPassphrase (session.ts:120-128) sets `expiresAt = now() + ttlMs` on every successful
read. Three independent violations defeat the control at once.

**Impact.** The rolling 30-minute auto-lock is the only bound on how long the vault passphrase and the
PBKDF2-derived AES key live in worker memory and in the chrome.storage.session plaintext mirror —
session.ts:98-105 shows clear() is what drops the passphrase and invokes onClear() to wipe the
derived-key cache (src/background/index.ts:130-134). None of that runs.

**Remediation (shipped).** Renewal is now a privilege rather than a side effect of parsing, on both halves of the
control, and destruction is time-driven. `PassiveUnlockSession` exposes only `peekPassphrase` and
`generation`, and every read that is not the user acting takes it: all dapp-reachable handlers, and —
the half that survived the first pass — the reads the side panel issues on its own. The panel refresh
loop, view hydration, and the three-second pending-registration poll re-read state with nobody
touching the wallet, so `wallet.multisigBalances`, `wallet.refreshMultisig`,
`wallet.multisigClassStatus`, and `wallet.strk20State` observed rather than renewed was the difference
between a fifteen-second cadence holding the vault open forever and the wallet locking on schedule.
Because those handlers share their account resolution with user-initiated ones, `multisigContext` and
`resolvePrivacyContext` now take the *resolved* account context instead of resolving it themselves,
so every call site names the privilege it is entitled to and a new one cannot inherit renewal by
accident. Expiry no longer waits for a reader: `src/background/index.ts` passes `chrome.alarms`
through `createBackgroundUnlockSession` to an `UnlockSessionExpiryTimer`, so an idle session and its
plaintext `chrome.storage.session` mirror are destroyed at the deadline (the `alarms` permission is
already declared and now documented for this second use). `createUnlockSession` takes a named
options object, so a caller can wire the timer without restating four positional arguments — the
shape that let production ship with no timer at all while every test that needed one passed five
arguments in the right order. Two suites pin the split by *trigger*, not by message:
`tests/background/dapp-poll-unlock-window.test.ts` derives its coverage from `DAPP_MESSAGES`, and
`tests/background/panel-poll-unlock-window.test.ts` derives its coverage from the loaders in
`src/sidepanel/hydrate.ts` and asserts the user-initiated routes still renew.

### MCW-V09-106

- **Severity:** Medium  |  **Area:** validation  |  **Status:** Resolved
- **Location:** `src/popup/approvals-responses.ts:345`

**Mechanism.** isPendingApprovalsResponse (src/popup/approvals-responses.ts:343-350) validates the whole queue as a
unit in two ways that each turn a single bad entry into total loss: `isJson(value)` applies ONE
JSON_BUDGETS.provider budget (1 MB / 50,000 nodes) to the entire `{ok, pending:[...]}` envelope
including every queued approval and every typedData inside it, and
`value["pending"].every(isPendingApproval)` fails the whole array on any single member. Three
independent triggers reach it.

**Impact.** Cross-origin denial of the wallet's consent surface with no user-visible symptom. Once wedged, the
user cannot see, approve, OR DENY any pending request — including a legitimate connect, invoke,
declare, or switch-chain prompt from an unrelated site queued before or after the spam. Those
requests stay live in the background queue (no TTL, no eviction), so the honest dapp's promise hangs
forever with no way for the user to reject it.

**Remediation (shipped).** The whole-envelope `isJson` is gone — each approval carries its own budget
through `isPendingApproval`, so the aggregate call added only the coupling — and `parsePendingApprovals`
now drops an invalid entry instead of rejecting the array, so one bad card can never hide the prompts
the user still has to approve or reject. Dropping is not the same as loosening: the envelope itself is
still all-or-nothing, and it gained the two bounds the aggregate gate used to supply — the shared
provider array cap, and a check that the `pending` array carries nothing but `length` and its own
in-range indices, since a validator that walks indices would otherwise miss an own non-index property a
later consumer still reads. Each slot is read through `isOwnDataProperty`, so hostile input cannot run a
getter or answer differently on a second read.

The panel half is the other half of the finding:
`packages/presentation/wallet-ui/tests/sidepanel/journeys/approvals/sidepanel-approval-queue-render.test.ts`
drives the real render path and asserts the honest prompt survives an unknown kind, an over-long
add-chain host, and a bogus fee unit queued beside it, while
`packages/presentation/wallet-ui/tests/popup/responses/popup-approval-queue-resilience.test.ts` pins
the reader, including that an approve/deny acknowledgement still works with a malformed prompt
queued behind it.

### MCW-V09-107

- **Severity:** Medium  |  **Area:** vault  |  **Status:** Resolved
- **Location:** `src/storage/preferences-store.ts:266`

**Mechanism.** src/sidepanel/settings-ui.ts:227-247 reads a user-chosen file, JSON.parses it, and calls
deps.wallet.importPreferences with no diff and no confirmation. src/background/preference-
inputs.ts:190-198 only requires a `preferences` record. src/storage/preferences-store.ts:266-272
validates with isWalletPreferences and then performs a wholesale `writePreferences(store,
candidate)` — no field is preserved, restricted, or shown to the user.

**Impact.** A single "restore my backup" action permanently and silently repoints the wallet's transaction-
review ground truth (token decimals and symbols, the unknown-contract warning, the address-poisoning
guard), its RPC endpoint, its NFT indexer — which then receives every account address the user
browses — and its STRK20 privacy pool and prover URLs. The user sees only a "Backup restored" toast.

**Remediation (shipped).** Option (a), tightened by one field. `pickImportablePreferences`
(`src/storage/preferences-entries.ts`) narrows a validated backup to the organisational fields alone —
`activeNetworkId`, `accountLabels`, `groups`, `hiddenTokens`, `theme`, `displayCurrency` — and
`importPreferences` merges that over the stored record, so every trust-bearing setting keeps its stored
value: RPC overrides, the NFT indexer URL, STRK20 pool and prover endpoints, custom networks, token
metadata, and the approval surface. Unlisted fields are dropped rather than merged, so a field added
later is excluded by default rather than admitted by omission.

`addressBook` is excluded too, which the finding's option (a) would have allowed. The contacts list is
what the address-poisoning guard compares a recipient against, so a hostile backup that plants or
relabels one contact turns the wallet's main anti-drainer control against its user; that makes it a
trust-bearing field, not an organisational one. The merge base is read defensively: a stored record this
build cannot read falls back to defaults rather than propagating, so a restore is also the way out of an
unreadable record. `tests/storage/preferences-import-scope.test.ts` pins field by field what a restore
may and may not change.

### MCW-V09-108

- **Severity:** Medium  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/starknet/verify.ts:209`

**Mechanism.** CALL_DECODERS (src/starknet/verify.ts:208-216) knows approve, transfer, transfer_from/transferFrom,
and safe_transfer_from/safeTransferFrom — but not increase_allowance/increaseAllowance.
unlimitedApprovalFlag short-circuits on `decoded.kind !== "approve"` (verify.ts:237-239),
unknownContractFlag returns null when the contract IS a tracked token (verify.ts:227-233), and
recipientForFlags returns "" for a non-transfer (verify.ts:274-281), nulling both recipient rules.

**Impact.** The wallet's primary anti-drainer control on the dapp invoke path is bypassed by a one-word change
to the selector — a spelling OpenZeppelin's Cairo ERC20 shipped for years. The user reviewing the
approval card sees `Call increase_allowance on 0x49d3…4dc7` with no spender, no amount, and no risk
panel, approves, and the spender receives a max-uint allowance on a real token — which the allowance
manager then cannot enumerate or revoke.

**Remediation (shipped).** The selector vocabulary is now one dependency-free module
(`packages/features/transactions/src/routing/verify-selectors.ts`) that the reviewer, the allowance
bookkeeping, and the swap build policy all classify against, so no spelling can be a grant to one
layer and opaque to another. Both increase spellings decode as kind `approve` with a spender/amount
summary and inherit the unlimited-approval flag, judged on the running total per (token, spender) so
a split grant cannot slip under the threshold. Resolving it in totality also covered the rest of the
same control: `set_approval_for_all`/`setApprovalForAll` decode as an `operator-approval` kind with
their own risk flag (a wider grant than any allowance, previously fully opaque); every submitting
path (dapp invoke, swap, multisig execution, pool submissions) files what it granted, before the
activity write and enforced by a conformance scan; the ERC20 arithmetic moved inside the allowance
store as one serialized `applyDelta`, so concurrent grants cannot lose an update; a delta applied
over a base this wallet never saw is stored as a lower bound and shown as "at least N"; and each
listed record's live `allowance(owner, spender)` is read directly, which reaches untracked tokens
and multisig-owned scopes that the event scan never could.

An ERC721 `approve(to, item_id)` is byte-for-byte an ERC20 `approve(spender, amount)`, so "is this a
spending allowance?" is answered from evidence at three points rather than assumed
(`approvedAssetKind`, `src/starknet/allowances.ts`, over the same trusted set `verificationContext`
builds for every other line). A collection this account WATCHES is never filed at all, so no item id
enters the log as an amount. A contract in neither the token registry nor the watch list is still
filed — a dapp's own ERC20 is the common case and an unrecorded grant can never be revoked — but the
manager lists it as `unconfirmedToken`, the panel prints the explanation instead of claiming units,
and no Revoke control is offered; `wallet.revokeAllowance` refuses it too unless the node answers
`allowance(owner, spender)` for that exact pair, a view an ERC721 does not have and the same node
that would have to relay the revoke anyway. The one direction that stayed open — sending
`approve(spender, 0)` at a collection the wallet had never been told about, which under ERC721
approves item #0 — is closed by that refusal.

Finally, a decrease no longer erases what it cannot bound: `increase_allowance(100)` over a base
granted elsewhere followed by `decrease_allowance(100)` used to delete the record, stranding a live
on-chain allowance with no row to list, revoke, or take a reading for. Flooring a LOWER bound (or
subtracting with no tracked base at all) now writes a zero-valued lower bound — "approved for an
amount this wallet cannot state", rendered as "an unknown amount" — which one `allowance(owner,
spender)` reading turns back into an exact figure. Only an EXACT zero, the `approve(spender, 0)` the
chain has stated, still clears the entry.

### MCW-V09-109

- **Severity:** Medium  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/sidepanel/transfer-submit.ts:75`

**Mechanism.** Three different policies for one control. (1) BLOCK — handleTransferNft refuses to submit on a
poisoning flag: `const poisoning = report.flags.find((flag) => flag.code === "address-poisoning");
if (poisoning) { return { error: poisoning.message }; }` (src/background/nft-ops.ts:342-345), and
the panel mirrors it by never enabling confirmation (src/sidepanel/nft-ui.ts:46-50 sets
`recipientBlocked`, nulls the reviewed key, sets stage "blocked", and relabels the button).

**Impact.** The wallet's anti-address-poisoning control — the single mitigation for the most common Starknet
drainer pattern, where the attacker dusts from an address whose leading and trailing hex digits
match a saved contact — is absent on three of four send routes and advisory-only on the highest-
value one.

**Remediation (shipped).** The gate is one exported function, `refuseOnPoisonedRecipient`
(`src/starknet/verify.ts`), applied at the enforcement point rather than per product line. It is
deliberately the only flag that refuses — `self-transfer` is ordinary for a shield or an unshield,
`unknown-contract` describes the contract the user chose, and an approval flag describes authority the
user may intend to grant. Placing it in the background is the point: a panel-side gate could only ever
be advisory because the panel's message is untrusted like any other, and
`src/sidepanel/transfer-submit.ts` now says so where a reader would otherwise re-add one.

The send lines that call it, each against a report built from the exact call that would go out,
before anything is broadcast, prepared, or queued for approval:

| Line | Enforcement point | Driven through the real handler by |
| --- | --- | --- |
| Public ERC20 send | `src/background/wallet-ops.ts` (before `submitErc20Transfer`) | `send-recipient-poisoning-parity.test.ts` |
| NFT send | `src/background/nft-ops.ts` | `send-recipient-poisoning-parity.test.ts` |
| Dapp invoke | `src/background/provider-ops.ts` (before the approval is queued) | `send-recipient-poisoning-parity.test.ts` |
| Wallet pool routes (shield / private send / unshield) | `src/background/strk20-send-ops.ts` at preparation and `src/background/strk20-wallet-ops.ts` at execute | `send-recipient-poisoning-parity.test.ts` |
| Multisig propose / confirm / execute | `apps/extension/src/background/multisig/multisig-tx-context.ts`, applied to the proposal's INNER call | `multisig-recipient-poisoning-parity.test.ts` |
| Dapp-facing STRK20 prepare / invoke | `src/background/strk20-ops.ts` at request time and `apps/extension/src/background/privacy/strk20-approval-execution.ts` after consent | `strk20-dapp-recipient-poisoning-parity.test.ts` |
| Swap execute | `src/background/swap-ops.ts` | not reachable through the real handler — see below |

Every refusal above has a clean-recipient counterpart in the same suite, so a check that refused
everything would fail too. Both routes that separate review from submission — the wallet's own pool
preparations and the dapp-facing invoke — re-apply the policy after the user confirms, because the
contact a recipient mimics can be saved while the confirmation is on screen; a gate only at request
time would leave exactly that window open. Two lines need their limits stated plainly rather than
glossed. The swap
execute gate is a genuine second line of defence but cannot be exercised end to end: `buildPolicy`
already refuses any aggregator build containing a decoded transfer, so no poisoned recipient survives
long enough to reach it; the shared policy under it is unit-tested. And the multisig line is the one
whose trusted set is widened — the watched multisig's own address is folded in alongside the address
book, because a treasury address is public on chain and is exactly what a duster mimics; it can only
add a refusal, never remove one. Revoking a confirmation is deliberately never gated: it is the way
out of a poisoned proposal.

The dapp-facing STRK20 line carries one carve-out, and it is a policy decision rather than a gap. A
privacy batch is reduced to calls by `strk20PolicyCalls`
(`apps/extension/src/background/privacy/strk20-recipient-policy.ts`) before the shared verifier sees
it: a `deposit`, `transfer`, or `withdraw` becomes a zero-amount ERC20 `transfer` probe of the token
it moves, and a `subaccount_invoke` contributes its real calls unchanged, because each one is a spec
INVOKE_CALL with a contract, an entry point, and felt calldata — the same shape
`wallet.addInvokeTransaction` accepts — and the SDK executes them verbatim through the anonymizer.
Routing a poisoned transfer through a dapp-scoped sub-account therefore refuses exactly as the
public invoke does. The flat `invoke` action stays ungated: its shape is `{type, contract,
calldata}` with **no** entry point, so there is no selector to decode and no argument position known
to hold a recipient, and the public route cannot express such a call either (`readProviderInvoke`
rejects a call without an entrypoint). Excluding it forfeits no parity; reading a recipient out of
an unattributed calldata slot would be a guess. Both halves are driven through the real handler in
`strk20-dapp-recipient-poisoning-parity.test.ts`, the sub-account one at request time, at
preparation, and after consent.

`tests/conformance/transfer-pool-route-recipient.test.ts` pins the panel's half — each pool route hands
the composed recipient through to the background and surfaces the refusal instead of swallowing it.
That suite needed the shared transfer harness to grow the three privacy preparation stubs it had never
had, which is why no pool-routed recipient had been driven before. Its expected wording is produced by
running the verifier (`tests/support/poisoned-recipients.ts`), never transcribed, so it cannot assert
on a sentence the wallet has never shown.

### MCW-V09-110

- **Severity:** Medium  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/background/token-ops.ts:103`

**Mechanism.** TokenConfig.id is `${networkId}:${symbol}:${address}` built by raw interpolation
(src/storage/preferences-entries.ts:79-82), upsertToken dedupes on exact id string equality, and
isTokenConfig accepts either spelling. Three canonical forms coexist: canonicalTokenAddress zero-
pads to 64 hex (src/background/watch-asset.ts:46-52), canonicalFelt/normalizeFeltInput produce the
minimal form (src/starknet/networks.ts:281-309), and the curated registry and DEFAULT_TOKENS store
the padded literal.

**Impact.** A user pasting a token address in its standard 64-hex zero-padded form — the spelling Starkscan and
Voyager display — for a token already tracked in the padded form (ETH and STRK are seeded that way
by default) creates a second record. Beyond the doubled balance row and doubled portfolio total, the
entire STRK20 privacy surface for that account then fails with "Private balances unavailable" on
every load, permanently, with no in-product way to remove the offending token or to discover why.

**Remediation (shipped).** One canonical spelling, enforced by the type rather than by call-site
discipline. `withTokenId` and `withAddressBookId` run the address through the shared `canonicalAddress`
before interpolating the id and store the canonical form back on the record, and `isTokenConfig` and
`isAddressBookEntry` both require `canonicalAddress(value.address) === value.address` — the same
strict-canonical rule `vault-account-secrets.ts` already applies to chain and pool ids. A record in any
other spelling is therefore not a valid record, so the invariant holds for stored data and not only for
the write path; records written before the rule are normalized on read.

The address-book half matters as much as the token half: a contact re-saved in a different spelling now
replaces the stored one instead of adding a near-duplicate to the very set the address-poisoning guard
compares recipients against. `tests/background/token-address-duplicate-records.test.ts` drives both
spellings of seeded Mainnet ETH through the real add-token handler and asserts one record survives;
`tests/storage/preferences-entry-canonical-address.test.ts` pins the validators.

### MCW-V09-111

- **Severity:** Medium  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `tests/support/key-boundary-messages.ts:345`

**Mechanism.** AGENTS.md designates tests/background/key-boundary.test.ts as the gate that "sanctions every path
that may expose secret material", and the catalog is enforced-derived. But the derivation (key-
boundary.test.ts:154-164) only asserts that every handled wallet.* TYPE STRING appears in the
catalog, and the scan loop (key-boundary.test.ts:203-220) serializes whatever the router returns and
greps it for the salted secrets — it never asserts the response was not a guard rejection.

**Impact.** The mechanism the project relies on to guarantee that no new message type can leak key material is
inert for 62% of the surface it claims to cover, and silently shrinks further every time an entry is
appended after index 64. The blind spot is concentrated exactly where the hard rules are: ALL twelve
wallet.strk20* types — the viewing-key and proof paths that "never expose or persist an STRK20
viewing key" exists for — plus wallet.transfer, wallet.transferNft, wallet.signTypedData,
wallet.addDecl …

**Remediation (shipped).** The scan is order-independent and positively asserted. Every catalog entry
starts from a freshly unlocked session, so one entry that locks the wallet can no longer turn every
entry after it into a `wallet locked` error the secret grep would wave through. A separate test then
asserts that each of the 104 entries reached a live handler — a non-error response — with an explicit
reviewed allowlist of the three meant to error (`wallet.status`, `wallet.unlock`,
`wallet.declareMultisigClass`), each carrying a written reason; that list is pinned by equality, so
excusing a fourth entry is a deliberate reviewed edit rather than the quiet way to make the suite green.

Two further tests stop the scan grepping a fiction. One pins, by exact list, which entries actually
cause the background to derive an account-scoped STRK20 viewing key — all twelve `wallet.strk20*` types
but the network-config write — because without a derivation the viewing-key grep is unarmed for that
entry. The other asserts the Ledger entries answer with shapes the popup validators accept, so the
stubs cannot answer with something production can never emit.
