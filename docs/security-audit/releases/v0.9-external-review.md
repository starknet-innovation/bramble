# v0.9.1 external security review

An independent reviewer audited the `v0.9` deep-audit remediation branch before promotion and
returned **DO NOT MERGE**, substantiating two High, six Medium, and seven Low findings. Every
finding was independently reproduced against the branch before any fix was written, and every
reproducer was re-run against the finished tree.

Severity definitions, method, and residual-risk conventions are the ones set out in the
[v0.9 deep adversarial audit](../v0.9-deep/). Findings are numbered `EXT-*` to keep them distinct
from the `MCW-V09-1xx` series they were found alongside.

Two of the fifteen findings were **regressions introduced by the v0.9 remediation itself**
(`EXT-M03`, `EXT-M04`) and two more were **incomplete remediations** of v0.9 findings
(`EXT-H01`, `EXT-L04`). Those are recorded as such rather than folded into the pre-existing set:
a control that was added and then got in its own way is a different failure from one that was never
built.

## Disclosure state

The reviewer's High findings were delivered privately. Both are Resolved, so this document records
the defect and the remediation; the reviewer's reproduction material stays out of the public record
and out of the repository.

## EXT-H01 {#ext-h01}

**Type-insensitive SNIP-12 scalars let numeric authority render as text**

- **Severity:** High  |  **Area:** signing receipt  |  **Status:** Resolved
- **Location:** `packages/platform/starknet/src/transactions/typed-data-values.ts`,
  `packages/presentation/wallet-ui/src/sidepanel/shared/sign-request-decode.ts`,
  `packages/presentation/wallet-ui/src/sidepanel/shared/sign-request-text.ts`
- **Origin:** incomplete remediation of `MCW-V09-101`/`MCW-V09-104`

**Mechanism.** The hashing gate asked one question of every leaf value: *is this a scalar?* The
declared SNIP-12 type was not consulted. The pinned library's leaf encoder is not symmetric — it
reads a value as a number whenever `BigInt` accepts it and as a short string otherwise, and
revision 0 range-checks nothing at all. Two consequences followed. A numeric field could carry
text that the encoder silently hashed as a large number, and a value's on-screen form could be
identical to another value's while the two hashed differently. The approval card compounded it: a
leaf reached the signed rows carrying neither its declared type nor the felt it encodes to, and
rendered through a plain string conversion that erases the difference between a JavaScript value
and the text spelling of it.

**Impact.** A connected site could obtain a valid signature over a numeric authorization — an
amount, a policy flag, a permit parameter — while the receipt the user read described something
benign. No hash collision and no key compromise were needed; the defect was a disagreement between
input validation, the library's encoding, and the wallet's own receipt. The collapsed raw-JSON
block is not a mitigation: it repeats the site's own spelling and explains no encoding.

**Remediation (shipped).**

- `packages/platform/starknet/src/transactions/snip12-scalars.ts` is the one type-directed reading of
  a leaf value, used by both the hashing gate and the approval card so what the wallet agrees to hash
  and what the card says it is hashing cannot drift. Each declared type admits only the JavaScript
  shapes it can mean: numeric types take canonical numeric text or a safe integer, `bool` takes a
  boolean, and the short-string family takes canonical numeric text or printable ASCII the library's
  own `BigInt` would refuse — so no accepted value reads as text on screen while hashing as a number.
- Ranges are enforced on both revisions, including revision 0 where the library checks none: a value
  outside its declared type's range is a lie about the type.
- Every accepted value carries the canonical felt the pinned library's own encoder produces for it,
  and `signValueText` prints the declared type and that felt beside every scalar. Site-chosen text
  keeps its quotes and its escaping.
- The felt is read back from the library's own `encodeValue` rather than re-derived, so the card
  cannot state an encoding the signing path would not produce.

**Tests.** `tests/starknet/typed-data-scalars.test.ts` and
`packages/presentation/wallet-ui/tests/sidepanel/journeys/approvals/sign-request-scalar-receipts.test.ts`
pin both directions: accepted aliases of one felt normalize to one receipt, and values with
different signed felts never produce byte-identical default receipts. Reverting the gate to the
pre-fix scalar predicate fails four of them.

**Behavioural note.** The gate is now stricter than the pinned library. A boolean under a numeric
or short-string type, and prose under a numeric type, are refused outright rather than rendered
with a warning. Both are values the library would have hashed; refusing them is the fail-closed
direction, and it is a visible compatibility narrowing worth carrying in release notes.

## EXT-M01 {#ext-m01}

**AVNU controlled the signed minimum output and beneficiary behind a benign swap review**

- **Severity:** Medium  |  **Area:** swap review  |  **Status:** Resolved
- **Location:** `apps/extension/src/background/transactions/swap-ops.ts`,
  `packages/presentation/wallet-ui/src/sidepanel/journeys/swap/swap-ui.ts`
- **Origin:** incomplete remediation of `MCW-V09-103`

**Mechanism.** `MCW-V09-103` bound the swap counterparty and entry point and left the route call's
calldata explicitly out of scope. A hostile-but-well-formed aggregator response on the correctly
pinned router could therefore name a different buy token, a zero minimum output, a third-party
beneficiary and a 100% integrator fee, and the review card's summaries and risk flags stayed
byte-identical to an honest build's. The confirm card made this sharper than an omission: it
rendered "Minimum received" and "Slippage cap: 0.5%" from the quote and a panel-local constant,
neither derived from nor checked against the calldata being signed — a positive false assurance
next to a row the same file had honestly labelled "not wallet-enforced".

**Remediation (shipped).**

- `packages/features/transactions/src/swap/avnu-route.ts` decodes `multi_route_swap` calldata against
  AVNU's exchange layout at a named upstream commit, recorded in the module header as a pin. Every
  accessor goes through the shared felt parsers, and any calldata it cannot read exactly returns null.
- `apps/extension/src/background/transactions/swap-build-policy.ts` binds the decoded route to a
  wallet-side intent: sell token and amount, buy token, this account as beneficiary, a minimum-output
  floor from the reviewed quote, and an integrator-fee ceiling. Every side of every equality is
  wallet-side.
- Exactly one route call is now admitted. The former "more than one swap call" flag is gone — once
  each call is bound to the full sell amount, a second is a duplicate demand on the one reviewed
  allowance that no receipt can honestly describe.
- The exact-out entry point is no longer admitted at all: the wallet only ever requests exact-in
  quotes, so decoding a second positional layout speculatively bought nothing.
- The confirm receipt now reads its minimum from the frozen preparation the background decoded out of
  the calldata it is about to sign, never from a panel-local slippage constant.

**Tests.** `tests/starknet/avnu-route.test.ts`, `tests/background/swap-route-binding.test.ts`, and
`tests/background/swap-build-policy.test.ts`. The triage reproducer's hostile build now fails at
prepare with "swap build bought a token you did not choose" and broadcasts nothing.

**Residual.** The layout is a pin: if the exchange is upgraded to a different route encoding, the
decoder stops recognizing builds and every swap fails closed until the new layout is read and
reviewed. That is the intended direction, and it is stated in the module header.

## EXT-M02 {#ext-m02}

**Response-budget failures disabled ambiguous-write protection on the private relay**

- **Severity:** Medium  |  **Area:** RPC classification  |  **Status:** Resolved
- **Location:** `packages/platform/starknet/src/rpc/provider.ts`,
  `packages/features/privacy/src/paymaster/paymaster.ts`

**Mechanism.** The reviewer reported this against the JSON-RPC read and write lanes; both were
measured working, because the pinned library rewraps whatever the wallet's transport throws before
any wallet code classifies it. The finding was real one boundary over. The STRK20 private relay
reaches its node through its own HTTP client, and every unreadable answer there — oversized,
unparseable, or ended by the client's own deadline — collapsed to a flat wallet error. The proof
maturity scope read that as a determinate rejection, released its `submitting` guard, and let the
next private action prove against note state that a possibly-landed write would have invalidated.

**Remediation (shipped).**

- `RpcTransportError` marks a JSON-RPC exchange that failed at the transport rather than at the
  node's application layer, and `isTransportRpcError` tests for it first. Read failover and
  accepted-write ambiguity no longer rest on a dependency's error rewrapping surviving a version
  bump. The reviewer's implied remedy — classifying every wallet error as transport — was rejected:
  genuinely semantic refusals must not fail over to the next endpoint.
- The paymaster client is now method-aware, mirroring the JSON-RPC lane's broadcast rule. Only the
  one relay method that puts a transaction on the wire mints the ambiguity marker; quote and build
  failures, and refusals the relay states for itself, stay determinate. A result carrying no usable
  transaction hash is treated as the worst case rather than a refusal — the relay answered with a
  *result*, so it accepted the submission and the wallet simply has no handle on it.
- The indeterminate-write sentence is one exported constant, so every submission lane mints the
  same line rather than three approximations.

**Tests.** `packages/features/privacy/tests/paymaster/paymaster-submit.test.ts` splits lost answers
from stated refusals, and `packages/features/privacy/tests/policy/maturity.test.ts` composes the real
paymaster client into the real maturity runtime end to end rather than injecting a stand-in error.

**Residual.** A held `submitting` scope is deliberately sticky and is cleared only by
reconciliation. This closes the lossy-channel case, not a relay that lies about having rejected a
transaction it forwarded; no classification at that boundary can, which is why the relay URL is
wallet-configured rather than dapp-supplied.

## EXT-M03 {#ext-m03}

**Merkle receipts were not injective over tree topology**

- **Severity:** Medium  |  **Area:** signing receipt  |  **Status:** Resolved
- **Location:** `packages/presentation/wallet-ui/src/sidepanel/shared/sign-request-decode.ts`
- **Origin:** regression introduced by `MCW-V09-104`

**Mechanism.** `MCW-V09-104` corrected a card that claimed leaf positions the hash did not commit
to, and over-corrected: it sorted all merkle leaves together and addressed them by a positionless
key, on the stated theorem that "every permutation of the leaves reaches the same root". That
theorem is false for the pinned library. Sibling *pairs* commute — the node hash sorts its two
operands — but the tree is built by pairing strictly on array index and padding a trailing odd
leaf against a constant, so moving a leaf into a different pair changes the root. The card
therefore printed one receipt for every distinct root over one leaf multiset: 3 roots at four
leaves, 45 at six, 315 at seven, all collapsing to a single card.

**Impact.** A site could obtain signatures over two or more distinct roots from cards the user
could not tell apart. The leaf multiset itself was rendered faithfully, so no leaf was added,
removed, or hidden; the harm is that the receipt was not injective on the signed hash, which breaks
any scheme treating a root as a one-shot commitment.

**Remediation (shipped).**

- `packages/platform/starknet/src/transactions/snip12-merkle.ts` mirrors the library's own pairing.
  `snip12MerkleLayout` normalizes exactly the exchanges the root is invariant under and no others: it
  pairs by index, orders the two children of each node by a canonical key derived from leaf *content*
  rather than from the payload's ordering, and leaves a padded trailing child in place. Leaves are
  addressed by the group they are hashed in — a run of `a`/`b` letters this wallet assigns — never by
  an ordinal, which would reintroduce the position claim `MCW-V09-104` existed to remove.
- The field's computed merkle root is reported as its own signed row, read back from the library's own
  encoder. It is emitted only for payloads the hashing gate accepts, so a refused payload still
  renders every leaf but never claims a root.
- The false theorem in the module doc was rewritten in the same change.

**Tests.** `tests/starknet/snip12-merkle.test.ts` and
`packages/presentation/wallet-ui/tests/sidepanel/journeys/approvals/sign-request-merkle-order.test.ts`.
The acceptance criterion — root and receipt are in bijection — was verified by exhaustive
permutation at every leaf count from two to seven: 1, 3, 3, 15, 45, and 315 roots respectively, each
with exactly that many distinct receipts. The sibling-swap invariance is pinned in the same suite,
so the fix cannot drift into over-separation either. Replacing the layout with the pre-fix global
sort fails five of these tests.

## EXT-M04 {#ext-m04}

**The new proposal-id binding blocked revocation of a poisoned confirmation**

- **Severity:** Medium  |  **Area:** multisig recovery  |  **Status:** Resolved
- **Location:** `apps/extension/src/background/multisig/multisig-proposal-guards.ts`,
  `apps/extension/src/background/multisig/multisig-tx-ops.ts`,
  `apps/extension/src/background/multisig/multisig-ops.ts`,
  `packages/presentation/wallet-ui/src/sidepanel/journeys/multisig/multisig-proposal-view.ts`
- **Origin:** regression introduced by `MCW-V09-102`

**Mechanism.** `MCW-V09-102` made every path that turns a stored proposal record into signed
calldata re-derive the transaction id from the stored call first. Revocation was included. But a
record whose id came from somewhere other than its own call is exactly the situation `MCW-V09-102`
exists to let a user back out of, and `revoke_confirmation`'s calldata is the id alone — the stored
call never reaches the wire. The strict gate therefore removed the only non-destructive exit from a
poisoned proposal while protecting nothing that is signed. Worse, the wallet's own error text
prescribed a remedy — re-track the proposal from the chain — that did not work, because re-tracking
preserved the poisoned call verbatim. The only escape was to remove the multisig entirely, which
deletes every proposal for it.

**Remediation (shipped).**

- `revokeRecordGuardError` turns revocation's hard refusal into an acknowledgment-gated recovery
  path, reusing the existing binding and untracked-verification guards rather than re-deriving
  either. Confirm and execute stay strictly refused: they attribute an id to a call, or sign the
  call itself.
- No new verification machinery was needed and none was added. The fresh chain read already
  requires the contract to report *this signer* confirmed *this exact id* before a revoke is built,
  so the recovery path cannot be steered onto an arbitrary id. The doc comment says so, to keep it
  from being re-tightened later. The reviewer's suggestion of a separate recovery message type was
  rejected — it would drag in the dapp-allowlist and key-boundary catalog derivations for no gain.
- Re-tracking a proposal now drops a stored call that does not hash to the resolved id, so the
  error text's own advice became true.
- The panel renders the acknowledgment affordance for unbound call-bearing records, importing the
  existing hash comparison rather than re-implementing it, so the background cannot accept a
  message the panel can never send.

**Tests.** `tests/background/multisig-stored-proposal-id-binding.test.ts` was rewritten rather than
relaxed: it keeps the confirm and execute refusals, adds the unacknowledged-revoke refusal, asserts
that what goes on the wire is the stored id and nothing else — no id derived from the untrusted
call, no felt of that call — and asserts that an acknowledged revoke of an id the chain says this
signer never confirmed is still refused. `tests/background/multisig-id-only-lifecycle.test.ts`
carries the id-only lifecycle that previously lived in a file now at its length limit.

## EXT-M05 {#ext-m05}

**Standard safe and batch NFT transfers bypassed the poisoned-recipient refusal**

- **Severity:** Medium  |  **Area:** recipient policy  |  **Status:** Resolved
- **Location:** `packages/features/transactions/src/routing/verify-selectors.ts`,
  `packages/features/transactions/src/routing/verify-decode.ts`

**Mechanism.** Enforcement read a field that decoding set. The recipient rule consulted the decoded
call's *kind*, and kind was only ever `transfer` when a summary decoder recognized the calldata
shape. The canonical five-felt ERC-721 safe transfer with an empty data span was one felt short of
the ERC-1155 decoder's minimum, and ERC-1155 batch transfers had no decoder row at all — so both
fell through to `unknown`, lost their recipient, and passed every enforcement point. The gap was
wider than reported: it covered `safe_transfer_from` and `safeTransferFrom` on ERC-721 at the two
most common span lengths, and every ERC-1155 batch spelling at any span. The vocabulary already
knew all four `*transfer_from` spellings and already said the recipient is the second felt; only
the gate in front of it was wrong.

**Impact.** The wallet's own NFT sends were unaffected, but any untrusted call source — a dapp
invoke, a stored multisig proposal, an aggregator-built call — reached the gap, and the review card
showed no recipient at all.

**Remediation (shipped).**

- `recipientFeltIndex(entrypoint)` states the recipient's position from the entry point alone, and
  the existing transfer-from predicate is re-expressed over the same list so the two cannot drift.
  Enforcement no longer consults the decoded kind. Spender-bearing selectors — approve,
  increase_allowance, set_approval_for_all — are deliberately excluded: their first felt is a
  spender, not a recipient.
- The summary decoders were extended in the same pass so the card describes what it refuses: an
  ERC-721 safe-transfer decoder, an ERC-1155 batch decoder, and an exact span for ERC-1155 single
  transfers, replacing summaries that previously reported an item id as an amount.

**Tests.** `tests/starknet/verify-nft-recipient-enforcement.test.ts`, including a drift test that a
spelling added to the vocabulary is enforced without a second edit. All fifteen transfer shapes the
triage enumerated now raise the poisoning flag and refuse; narrowing the recipient index to exclude
safe transfers fails five of these tests.

**Behavioural note.** A dapp NFT transfer to a lookalike of a saved contact is now hard-refused
rather than merely annotated. That matches the ERC-20 lane and is intended, but it is user-visible.

## EXT-M06 {#ext-m06}

**Wallet-initiated transactions signed fees the user never reviewed**

- **Severity:** Medium  |  **Area:** transaction authorization  |  **Status:** Resolved
- **Affected:** account and multisig deployment, multisig declaration/propose/revoke/execute,
  allowance revoke, and swap execution

**Mechanism.** The submit boundary correctly constrains resource bounds when a caller supplies
`reviewedFee`, but deliberately remains unbound when it does not. The dapp approval and ordinary
send paths already carried the fee displayed by their review. The wallet-initiated lanes above
did not display or supply one, so a configured RPC could inflate its quote and the wallet would
sign the resulting bounds without an amount-specific user decision.

**Remediation.** Every affected operation now has a fail-closed two-step protocol. The first call
builds the exact operation, estimates its fee, and returns only a strict `feeReview` response. The
panel displays that amount and the confirming call echoes it. The background accepts only the
shared `FeeEstimate` grammar and passes the echo to the existing resource-bounds enforcement.
Declare and deployment reviews now state the maximum spend implied by the quoted resource bounds,
not the node's smaller headline fee. Missing or failed estimates submit nothing. Swap preparations
store the estimate background-only and bind it into the preparation digest; multisig operation
claims are acquired only after fee review, so requesting a quote cannot consume or race a submission
slot. A failed submission clears the panel's cached review so retry always obtains a fresh estimate.

*Tests:* `tests/background/transactions/background-deployment-messages.test.ts`,
`tests/background/portfolio/background-allowance-messages.test.ts`,
`tests/background/transactions/swap-ops.test.ts`,
`tests/background/multisig/background-multisig-messages.test.ts`, and the existing bound-enforcement
tests in `tests/starknet/rpc-submit-fee-bounds.test.ts`.

## Lower-severity findings

### EXT-L01 {#ext-l01}

**Reviewed fee re-read at approve time.** *Resolved.* The submission ceiling read the queue's
current fee at claim time rather than the figure the card displayed, so a re-estimate from a second
open wallet surface could raise the enforced ceiling far above what the user read; concurrent
retries were also last-write-wins, so an older estimate resolving late replaced a newer one.
`wallet.approveOrigin` now carries the fee the deciding card painted, validated by the same fee
guard the send lanes use, and a decision whose echo disagrees with the queue is refused rather than
silently substituted. A decision that echoes no fee submits unbound — the same treatment a review
that could not be priced already got. Fee slots are claimed before each estimate starts, so a
superseded write lands nothing at all, marker included.
*Tests:* `tests/background/reviewed-fee-binding.test.ts`,
`tests/background/approvals/approval-fee-queue.test.ts`.

### EXT-L02 {#ext-l02}

**Viewing key derived after an explicit lock.** *Resolved.* Two thunks built one object literal
apart behaved differently: the signing thunk re-checked the authorizing unlock before and after
each call, and the viewing-key thunk closed over the passphrase with no session predicate at all,
so a private-balance disclosure could complete after the user locked the wallet. The viewing-key
thunk now takes the same before-and-after check. The second, unbound copy in the dapp invoke
executor was deleted in favour of the bound one rather than given a third guard.
*Tests:* `tests/background/privacy/strk20-account-context.test.ts`,
`tests/background/strk20-vault-sign-lock-revocation.test.ts`; the assertion is that the derivation
is never invoked, not merely that it throws afterwards.

### EXT-L03 {#ext-l03}

**Unlimited-approval total started at zero.** *Resolved.* The rule accumulated only the calls in
the transaction under review, so a one-wei top-up on a standing allowance just below the threshold
crossed it on chain and raised nothing. The verifier stays network-free; the caller now supplies
starting totals from the wallet's own allowance log, seeded only for contracts classified fungible
so an ERC-721 item id can never be read as a standing amount. A read failure seeds nothing and the
rule falls back to the network-free reading, which can miss a flag but never invent one.
*Tests:* `tests/starknet/verify-increase-allowance.test.ts`, which keeps the unseeded case as an
explicit control. *Residual:* seeding is wired on the dapp invoke queue path; the in-wallet send
review still judges an increase on its own.

### EXT-L04 {#ext-l04}

**Dapp invokes did not re-check a changed trusted-address set.** *Resolved.* The recipient policy
ran when the approval was queued, and the card's flags froze there. A contact saved while the
prompt sat open turned a payee into a lookalike that neither the card nor the executor noticed.
The executor now re-applies the same shared gate to the exact calls about to be broadcast, which is
verbatim reuse of the queue-time check and of the check the STRK20 executors already ran — this was
the missing half of `MCW-V09-109`, whose parity claim was overstated.
*Tests:* `tests/background/send-recipient-poisoning-parity.test.ts`.

### EXT-L05 {#ext-l05}

**Multisig operation claims omitted the multisig contract.** *Resolved (availability).* The
in-flight claim key namespaced by network and account but not by the multisig, while the sibling
proposal key did — so one transaction id, which the propose form's default salt makes easy to
collide across treasuries, wedged a second multisig behind the first's claim with an error
describing a state the user did not have. The reviewer framed this as a defect in the wallet's
transaction-id derivation; it is not, and that remedy was rejected: the derivation mirrors the
deployed multisig component and is cross-checked on chain, so changing it would convert an
availability annoyance into a total multisig outage. The claim key gained an optional owning-multisig
component instead. Claims written before the namespace existed keep their original key, so the
change frees no live claim by renaming it, and the registry is plain data outside the encrypted
vault — no schema step is involved.
*Tests:* `tests/background/multisig-proposal-claim-scope.test.ts`, including the legacy key shape.

### EXT-L06 {#ext-l06}

**Execute and revoke could both broadcast.** *Resolved.* Claims were separated by kind, so an
unresolved claim of a different kind was invisible: a signer could broadcast an execute and then a
revoke on the same proposal, because until the first mines the chain still reports the pre-action
state and both guards pass. Any unresolved proposal action by this signer now blocks the opposite
one. Retryability is preserved — a rejected or reverted action frees the slot — and that is pinned
directly, so an over-strict version cannot wedge a signer whose execute reverted.
*Tests:* `tests/background/multisig-proposal-claim-scope.test.ts`.

### EXT-L07 {#ext-l07}

**Legal typed data consumed CPU before a full queue was refused.** *Resolved.* The per-origin
approval cap bounded memory but not CPU: it was applied at the end of each dapp handler, so a
maximum-size SNIP-12 document was fully hashed and the vault was decrypted to read the origin's
grants before the queue refused the request and discarded all of it. A connected site could keep
the service worker — which also serves the side panel — saturated with requests it was always going
to refuse. The queue now exposes an admission probe, applied immediately after the origin and
blocklist gates on every dapp surface that queues a non-deduplicating approval. The real gate stays
inside admission, so the cap cannot become caller-dependent, and deduplicating surfaces
deliberately do not probe.
*Tests:* `tests/background/approval-admission-ordering.test.ts`, which asserts the ordering as an
invocation claim — a refused request must not reach the vault at all — rather than as a timing one.
*Note:* the refusal a content script sees is still the generic failure line, deliberately: the cap's
own wording would tell a flooding origin what it hit.

## Verification

Every reproducer written during triage was re-run against the finished tree and no longer
reproduces. All seven offline gates pass, and on a machine carrying the vendored artifacts the
