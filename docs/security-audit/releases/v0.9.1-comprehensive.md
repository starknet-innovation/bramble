# v0.9.1 comprehensive adversarial security audit

multisig contract and build/release controls at
`631163bb0bd1cee57886af6595c67732594fe2cc`. It found no Critical or High issue, four Medium
issues, eight new Low issues, one previously accepted Low residual, and four Informational
hardening items.

The release is **not security-cleared** while `MCW-V091-001` through `MCW-V091-004` remain open.
Passing automation is strong supporting evidence, not evidence that these reproduced faults are
safe.

## Security model and end-to-end trust graph

```text
untrusted page JavaScript
  -> injected provider (page world)
  -> content bridge (isolated world)
  -> chrome.runtime sender metadata
  -> privileged background router
  -> origin/grant/account/network/approval/session gates
  -> KMS or exact Ledger device signer
  -> Starknet / privacy / indexer / metadata service
  -> post-broadcast allowance, activity, and operation journals

extension pages
  -> privileged runtime messages
  -> the same background policy and signing boundaries

chrome.storage.local
  -> encrypted versioned vault or validated feature stores
chrome.storage.session
  -> memory-only unlock mirror, restricted to trusted extension contexts
```

The audit treated the page, message body, browser sender metadata, storage, RPC, SDK, indexer,
metadata, hardware response, build host, and CI configuration as independently hostile or
failure-prone. It followed both dapp-initiated and wallet-initiated actions through final signing,
broadcast, bookkeeping, restart, retry, and failure reporting. It also tested direct page messages
that bypass the friendly provider API, multiple wallet surfaces, lock/expiry races, old encrypted
state, out-of-order asynchronous completion, and failures after a transaction is already live.

## Open Medium findings

### MCW-V091-001 — A successful broadcast can be reported as a failed submission

**Area:** transaction outcome integrity and idempotency.

ERC-20, NFT, dapp invoke, swap, allowance, deployment and public/private STRK20 paths await local
activity or allowance persistence after receiving an accepted transaction hash. Several handlers
catch a later storage failure in the same failure boundary as the broadcast and discard the hash.
The wallet then tells the user or dapp that submission failed; ERC-20 and NFT copy explicitly says
nothing was sent. A retry can broadcast the same economic action again under a new nonce.

A fault-injected message-path reproduction observed one accepted broadcast while both the approval
decision and held dapp request returned an error. Existing tests verify that allowance bookkeeping
survives the same fault but do not require preservation of the transaction hash. Declare and
multisig already demonstrate the correct invariant: post-broadcast journals are best-effort and
cannot rewrite the chain outcome.

**Affected boundaries:** background account transfer, NFT transfer, provider invoke, swap,
allowance/deployment, STRK20 approval and wallet preparation handlers; corresponding wallet UI
failure states.

**Required invariant:** once a valid broadcast response exists, every caller receives the hash and
an honest submitted/pending outcome. Security-critical bookkeeping uses a durable pre-broadcast
claim or a recoverable warning, never a false submission failure.

**Retest:** inject failures independently into Activity, allowance, and operation-hash stores for
every submitter; require exactly one broadcast, the original hash in the response, no retry-ready
“not sent” state, and eventual reconciliation.

### MCW-V091-002 — Fee consent is not universal across value-moving operations

**Area:** reviewed authority and RPC trust.

The ordinary deployed-account invoke path binds the exact fee rendered to the user to the resource
bounds later signed. That invariant is absent in two normal product families:

- public-account STRK20 registration and deposit review and bind the pool fee but neither estimate
  nor bind the Starknet network fee; and
- ERC-20/NFT submit messages accept a missing reviewed fee. The normal undeployed-account journey
  reaches that state, displays that gas will be determined later, then permits automatic deployment
  and transfer with neither deployment nor invoke fee bound to user consent.

These are not arbitrary-call bypasses. STRK20 still pins the configured pool, SDK-built
`apply_actions`, exact deposit actions, account, network, recipient and pool fee. Extension-only
transfer messages are unreachable from ordinary content scripts. The defect is that a high live fee
or chain-matching hostile RPC can influence the maximum spend signed without an amount-specific
decision; an inflated bound is not proof the entire bound will be charged.

**Required invariant:** every wallet-funded transaction, including automatic deployment, has a
fail-closed fee review whose exact call batch and fee are frozen, displayed, echoed and enforced at
the signing boundary. Private paymaster-sponsored relay actions remain a separate route.

**Retest:** omission, failed estimate, changed estimate, undeployed account, registration and
deposit must submit nothing. A matching echoed estimate must reach the exact invocation and any
preceding deployment as separate ceilings.

### MCW-V091-003 — An authentic old vault can roll back current authority

**Area:** encrypted storage freshness.

AES-GCM authenticates ciphertext and binds it to the vault storage scope, but the envelope has no
monotonic freshness authority. A captured authentic v4 envelope written back later decrypts and is
accepted as current. The reproduced rollback reinstated a revoked origin grant without knowing or
modifying the passphrase-protected contents.

An ordinary page or content script cannot write extension storage because startup requires trusted
storage access. The prerequisite is stronger: capture and later write access through the browser
profile/filesystem, a compromised trusted extension context, backup/profile rollback, or a
compromised release. Within that model, rollback can reinstate old grants and retained Ledger
viewing keys, change the active account, or remove newer account/import state.

**Required invariant:** a vault state older than the last accepted commit cannot become current
merely because its ciphertext is authentic. The freshness authority must not roll back with the
vault itself.

**Retest:** write generations N and N+1, restore N, restart the worker and unlock; the wallet must
detect rollback before exposing grants, secrets or account selection. Migration/recovery staging
must retain its crash-safe behavior.

### MCW-V091-004 — A page can force unbounded metadata RPC work before admission

**Area:** provider availability and request admission.

The injected provider's 100-request pending cap is not a trust boundary. Any ordinary page can
construct the public bridge envelope and send valid same-window `postMessage` requests directly to
content. Content forwards each valid request without an in-flight or rate limit. For
`wallet_watchAsset`, background resolves token metadata before attempting approval-queue admission;
real metadata resolution fans out three RPC calls.

Real-module probes forwarded 101 direct page messages despite the provider cap, observed 101
concurrent metadata resolutions before any approval insertion, and still performed a sixth
metadata lookup when the origin's five approval slots were already full. The overflow eventually
fails, but only after attacker-controlled RPC work. This is resource and provider-quota exhaustion,
not a signing or authorization bypass.

**Required invariant:** reserve a bounded per-origin and global in-flight slot before any remote
work, apply the bound to every page envelope rather than only the friendly API object, and preserve
safe deduplication of an already-pending watch-asset review.

**Retest:** direct bridge messages above the bound must perform no extra preferences or metadata
RPC work; a full approval queue must reject before RPC; concurrency must remain bounded across
multiple frames, tabs and origins.

## Informational hardening and consistency items

1. **Session-mirror erasure trusts the storage API contract.** `mirrorCleared()` treats a resolved
   remove as completion without readback. A deliberately contract-violating no-op store can restore
   the passphrase in a new worker. Chrome promises completion on a resolved remove, so this is not a
   demonstrated browser vulnerability; readback or a revocation marker on every clear would add
   defense in depth.
2. **Privileged input budgets are inconsistent.** Extension-only mnemonic/passphrase fields have no
   explicit character cap, and Ledger account derivation accepts an unbounded array then fans out
   with `Promise.all`. The production UI emits 12/24 words and Ledger pages of five; ordinary pages
   cannot reach either message.
3. **Runtime DTOs remain redundant.** Background and presentation separately declare
   `WalletStatus`, `PendingApproval`, `ConnectedSite` and `NetworkOption`. The UI validates network
   IDs but types them as `string`; it also accepts a missing approval `kind` as legacy connect even
   though the current producer requires `kind`. Independent parsing is correct, but the wire model
   should be single-sourced so impossible legacy states do not persist indefinitely.
4. **Multisig configuration could reject more hostile RPC shapes.** The decoder bounds signer count
   and validates felts but does not independently reject duplicate signers or `quorum > signer
   count`. On-chain enforcement prevents authority bypass; a malicious RPC can still confuse the
   watched configuration or induce wasted attempts.

## Disproven leads and verified invariants

- Arbitrary STRK20 approval is not opaque: exact token, amount, recipient, contract, entrypoint,
  calldata, nonce and collection policy are rendered, validated and digest-bound. The terse summary
  is supplementary, not the consent record.
- A page cannot reach new privileged `wallet.*` handlers by default. The public method registry
  derives the dapp allowlist, privileged messages require an extension-page sender, and the
  key-boundary catalog covers every handled message.
- Page-local forged provider responses or events can only corrupt that page's own JavaScript view;
  they do not mint background authority.
- Lock/expiry revokes software signing and STRK20 viewing-key work before and after asynchronous
  secret use. Parked Ledger signs are removed and device completions are generation-checked.
- No fallback key derivation, signing, mnemonic validation or secret logging path was found. KMS
  absence and malformed outputs fail closed.
- Software viewing keys remain derived on demand and unpersisted. Retained Ledger viewing keys are
  encrypted and bound to the exact account, chain, pool and scheme.
- Vault migrations are adjacent, deterministic, staged, readback-verified, serialized and
  crash-recoverable. AES keys are non-extractable, cached with a bound and cleared on lock.
- RPC reads have chain checks, 15-second request deadlines and a 32 MiB response cap. Writes select
  one endpoint before mutation, never retry a possibly accepted broadcast, and require non-zero
  success hashes.
- Dapp approvals atomically claim once, bind origin/account/network/chain/payload, recheck live
  grants/blocklist/policy, and fail closed on changed fees.
- Typed-data validation covers revision vocabulary, type graphs, tuples, enums, Merkle values,
  resource budgets and account-inclusive hashing.
- Recipient poisoning is enforced across ERC-20, NFT, swaps, multisig, dapp invokes and STRK20.
- AVNU routes bind router, tokens, sell amount, minimum output and beneficiary. Multisig proposals
  are locally hashed, rehashed before action and protected by durable scoped operation claims.
- NFT discovery does not trust indexer ownership, and unsolicited NFT images are not fetched until
  explicit reveal. The sandbox browser tests blocked script/network escape, nested frames, SVG and
  malformed input.
- Manifest permissions, CSP, web-accessible resources and the 16 packaged paths match their exact
  checked allowlists. No remotely hosted executable code or production testkit dependency appeared.
- All action uses are SHA-pinned, workflow token defaults are read-only, selected-actions mode and
  SHA-pin enforcement are enabled, and no open CodeQL, Dependabot or secret-scanning alert existed
  at audit time. Three current CodeQL HTML findings were reviewed and dismissed with concrete
  escaping/closed-type evidence; older alerts are fixed.

## Limits and required follow-up

No live fund-moving mainnet test was run: the repository correctly requires explicit secrets and
acknowledgements, and an audit does not authorize spending. No physical Ledger/BLE/WebUSB/WebHID
device, real prover/paymaster, hostile live RPC, Chrome Web Store upload, or independent Krusty
builder was available. JavaScript strings and browser `CryptoKey` objects cannot promise native
zeroization. There is no account-deletion API in this baseline, so deletion cleanup is a future
proof obligation rather than an audited feature.

Remediation priority is:

1. Preserve accepted transaction hashes across every post-broadcast bookkeeping failure.
2. Make reviewed network/deployment fees mandatory for every wallet-funded route.
3. Design and test rollback-resistant vault freshness without weakening crash recovery.
4. Move page-controllable resource admission before RPC work.
5. Serialize provider event refresh and close the remaining session, identity, KMS, type and
   repository-assurance Low findings.

After fixes, rerun the complete release gate, fault probes, browser E2E, deterministic packaging,
exact-head CodeQL/CI, and a separate adversarial review of the remediation. Only then should this
record be sanitized, published and linked from the public findings ledger.
