## Executive summary

The v0.6 pass reviewed the new Ledger hardware-wallet boundary end to end and then re-audited the
multisig submission, persistence, synchronization, and side-panel paths. No fund-loss or
security-bypass defect remains open in the reviewed scope. Six grouped robustness, state-integrity,
and assurance findings were fixed before release.

Ledger secrets do not cross extension channels or enter the vault. The grant popup conveys no
device data or signature: it only causes Chrome to record an origin-scoped WebHID permission.
Signing remains fail-closed, checks the expected device public key, verifies the returned
signature, and broadcasts only after verification. Ledger-only vaults contain public account
metadata without a mnemonic or signing key.

Multisig submission now distinguishes an accepted chain transaction from later local bookkeeping
failure. Declare/deploy intents are claimed durably before broadcast; pending state fails closed;
and UI state cannot turn an RPC or storage failure into a false empty, settled, or signer-confirmed
result.

## Reviewed trust boundaries

- Chrome side panel ↔ short-lived Ledger grant popup ↔ browser-owned WebHID permission.
- Side panel Ledger transport ↔ Ledger Starknet application APDU interface.
- Background signing queue ↔ active account, network, unlock session, and expected Ledger public key.
- Returned Ledger signature ↔ Stark curve verification ↔ single broadcast chokepoint.
- Encrypted vault migration from mnemonic-backed records to mixed and Ledger-only records.
- Multisig UI/RPC response guards ↔ permissioned store ↔ background submission operations.
- Chain broadcast result ↔ durable operation claim, activity log, and proposal cache.

## Findings

<a id="mcw-v06-001"></a>

### MCW-V06-001 — Partial Ledger account onboarding could wedge retries

**Severity:** Low; **Status:** Resolved

A failed multi-select batch could create some accounts, hide them from the result, and retain stale
duplicate detection. The onboarding session now commits each successful addition to visible state
and refreshes duplicate knowledge before a retry. Partial success is recoverable and cannot loop
indefinitely.

<a id="mcw-v06-002"></a>

### MCW-V06-002 — Ledger transport compatibility and grant lifecycle were too broad

**Severity:** Low; **Status:** Resolved

The Buffer compatibility layer was panel-global, a grant popup that failed to close could leave
connect waiting indefinitely, and multiple granted devices were selected by browser enumeration
order. Buffer is now scoped to the Ledger module boundary; the popup wait has timeout and
closed-window detection; and the user explicitly selects among multiple granted devices. The
wrong-device public-key check and verify-before-broadcast gate remain final defenses.

<a id="mcw-v06-003"></a>

### MCW-V06-003 — Multisig submission outcome could be lost or duplicated

**Severity:** Medium; **Status:** Resolved

After a successful broadcast, a local activity or store failure could return a false operation
failure and lose the transaction hash. Declare/deploy duplicate protection also depended on
non-atomic activity history that aged out. Submission now records a durable atomic operation claim
before broadcast, preserves the returned hash despite later local-write failure, and releases only
claims whose chain result is known to permit a retry.

<a id="mcw-v06-004"></a>

### MCW-V06-004 — Multisig read failures could fabricate chain state

**Severity:** Medium; **Status:** Resolved

Activity read failure could downgrade a pending proposal, and list/detail RPC or storage errors
could render as no multisigs or no longer watched. The pending check now fails closed. List/detail
refresh on entry, retain previously validated data on failure, expose explicit error/retry state,
and label the synchronization boundary. Cached signer confirmation is scoped to the active account
and is not trusted across account changes.

<a id="mcw-v06-005"></a>

### MCW-V06-005 — Impossible multisig actions reached privileged handlers

**Severity:** Low; **Status:** Resolved

Confirm/revoke and proposal actions were not consistently gated by fresh signer state, and deploy
did not present a distinct no-account state. The side panel now disables actions that the current
account cannot perform, prevents acknowledgement controls from re-enabling a forbidden action,
and shows the no-account deployment boundary explicitly. Background validation remains
authoritative.

<a id="mcw-v06-006"></a>

### MCW-V06-006 — Release assurance and recovery documentation had gaps

**Severity:** Informational; **Status:** Resolved

The side-panel multisig RPC client, response guards, hydration, and action UI lacked focused tests;
the multisig artifact comment pointed at a nonexistent file; and mixed-wallet backup copy did not
state that the software recovery phrase excludes Ledger accounts. Dedicated regression suites,
the corrected artifact path, and explicit recovery copy now cover those boundaries.

## Ledger protocol verification

The review checked the shipped package against the real Ledger Starknet API rather than a local
stub:

- EIP-2645 paths use the expected `2645'/1195502025'/account'/0'/0'` form.
- Public-key extraction uses the Starknet app response layout and its actual byte offset.
- APDU status handling matches the Ledger transport error codes used by the dependency.
- Signature parsing takes the expected `r` and `s` slices and rejects malformed or non-field values.
- Every Ledger submit path performs expected-device precheck and signature verification before
  its one permitted broadcast.
- Explicit wallet lock cancels queued and in-flight signing and prevents a late result from
  crossing the revoked session boundary.

## Residual boundaries

This review did not audit Ledger firmware, Chrome's WebHID implementation, RPC nodes, or the
upstream Ledger libraries internally. Physical-device evidence was supplied by the integration
tester rather than independently reproduced during the source pass.

`@ledgerhq/hw-app-starknet` 3.0.2 declares a `starknet` peer range below the repository's
`starknet` 10.0.2. The wallet invokes only `getAppVersion`, `getPubKey`, and `signHash`, not the
SDK-dependent clear-signing APIs; source review, build, automated tests, and physical E2E validate
that used boundary. The peer warning remains a tracked third-party compatibility risk and should
be retested when either dependency changes.

The audit establishes the reviewed commit's controls, not an absence-of-defects guarantee. Any
change to Ledger APDUs, derivation, signature parsing, session cancellation, vault migrations,
multisig submission claims, or account-scoped signer state requires renewed focused review.
