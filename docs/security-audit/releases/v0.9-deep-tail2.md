# v0.9 deep audit — low findings, `MCW-V09-121`..`129`

Continuation of the [low findings](../v0.9-deep-tail/), split to stay within the repository's
500-line file budget. Method, verification, and residual boundaries are defined in the
[parent document](../v0.9-deep/).

### MCW-V09-121

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/starknet/provider.ts:41`

**Mechanism.** createRpcProvider (src/starknet/provider.ts:41-45) passes only `{...options, nodeUrl, specVersion}`
and never sets baseFetch, so starknet.js falls back to a bare fetch with no AbortSignal.

**Impact.** The multi-endpoint failover the network config is built around is inert against the most common real
failure mode — a black-holed connection rather than a refused one.

**Remediation (shipped).** `createRpcProvider` sets `baseFetch: timedRpcFetch()` itself, so every
provider in the wallet is deadline-bounded by default and a new lane inherits the bound instead of
re-deriving it; the multisig read lane overrides only the number. A conformance scan walks `src/` and
fails if any module outside `provider.ts` builds a provider transport of its own.
`tests/starknet/rpc-provider-timeout.test.ts` pins that a black-holed endpoint aborts and fails over.

### MCW-V09-122

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/background/index.ts:220`

**Mechanism.** Three transports are wired as bare pass-through fetches with no AbortSignal and no size cap: the
price feed at src/background/index.ts:191 (`http: (url) => fetch(url)`), the phishing feed at
index.ts:220 (`fetch: (url) => fetch(url)`), and the NFT indexer at src/background/runtime-
rpc.ts:183.

**Impact.** A hostile or compromised third-party host can hang the request indefinitely (no timeout) or make the
MV3 service worker buffer an arbitrarily large body into its heap before any cap applies, evicting
the worker.

**Remediation (shipped).** `packages/foundation/core/src/http-json.ts` is the single bounded reader:
one deadline covers connecting, headers, and every body chunk, and the byte budget is spent AS THE
BYTES ARRIVE — the stream is cancelled the moment it is exceeded. That distinction is the finding,
not a detail: a boundary that buffers a body and measures it afterwards has already paid for the
body it was trying to refuse, which is exactly what Starkscan's `await response.text()` then
`text.length > MAX` did. Every untrusted boundary now goes through it — the price feed, the phishing
list, the NFT indexer, Starkscan (both its success body and the error body it reads back), and the
AVNU swap aggregator — each with its own declared budget in `HTTP_BODY_LIMITS`.

The hardening the reader composes (no cookies, no referrer, redirects refused, and the deadline as
an `AbortSignal`) only reaches the socket if the wiring forwards it, and for three of those five it
did not: the price feed, the phishing list, and the NFT indexer were wired `(url) => fetch(url)`,
which type-checks — TypeScript accepts lower arity — and silently discards all of it. The caller
still got its deadline, because the reader races it wallet-side, so nothing looked broken while the
request stayed in flight forever and a hostile 3xx was followed wherever it pointed (a redirected
phishing feed answering `{"blacklist":[]}` removes protection outright). There is now one shared
`untrustedFetch` in `packages/foundation/core/src/http-json.ts` and every boundary names it, so a
wiring site has nothing left to get right. `tests/conformance/untrusted-fetch-wiring.test.ts` drives
the REAL indexer and phishing feed against a local redirecting server, watches a local server
observe the disconnect when the deadline expires, and scans `src/` for any single-argument `fetch`
wrapper — the injected transport assertions elsewhere are structurally blind to this, which is how
it survived a round of remediation with tests green.

The Starknet JSON-RPC lane is a separate transport and the wallet's largest untrusted boundary — a dapp
can propose its URL through `wallet_addStarknetChain`, and starknet.js reads the body with `.json()`.
A deadline alone is not a bound there: at a modest link speed one 15-second request buffers well over a
hundred megabytes. `timedRpcFetch` reads that body through the same stream-capped reader under the
request's own deadline (`RPC_BODY_LIMIT_BYTES`, 32 MiB — generous over a Sierra class, the largest
legitimate answer) and re-presents it, so `.json()` only ever sees bytes the wallet agreed to hold. The
multisig read lane had defined its own `baseFetch`, which REPLACED a caller's abort signal instead of
composing with it; it now overrides only the NUMBER, and a test walks `src/` to assert no module
outside `provider.ts` builds a provider transport of its own.

The two remaining private readers, in `nft-token-metadata.ts` and `strk20/paymaster.ts`, were checked
rather than assumed: both already cap on the stream, so neither is a defect.

`tests/starknet/http-body-bounds.test.ts` drives each boundary with an endless body and asserts how
much the endpoint managed to emit before it was cut off, which is what distinguishes a streaming cap
from a post-hoc one; `tests/starknet/http-bounded-fetch.test.ts` covers the reader's deadline
behaviour, including a body that stalls mid-stream without ever tripping the size cap.

### MCW-V09-123

- **Severity:** Low  |  **Area:** validation  |  **Status:** Resolved
- **Location:** `src/storage/activity-store.ts:379`

**Mechanism.** csvField (src/storage/activity-store.ts:379-380) quotes a value only when it contains a quote,
comma, or newline — RFC-4180 delimiting, which is not a formula guard: Excel, LibreOffice, and
Google Sheets evaluate a cell whose content begins with `=`, `+`, `-`, `@`, TAB, or CR regardless of
surrounding quotes.

**Impact.** Opening the exported activity CSV in a spreadsheet executes attacker-authored formulas in the user's
desktop context: `=HYPERLINK(...)` exfiltrates adjacent cell contents — the account address,
transaction hashes, counterparties — to an attacker URL on a singl …

**Remediation (shipped).** `csvField` prefixes a single quote before the RFC-4180 quoting whenever the
cell would open a formula, judged both on the raw value and on the value with importer-skippable
padding stripped — so ` =1+1`, a NUL-prefixed payload, and a bare `=1+1` are all neutralized.
`tests/storage/activity-csv-formula-injection.test.ts` pins each lead character and the padded forms.

### MCW-V09-124

- **Severity:** Low  |  **Area:** authz  |  **Status:** Resolved
- **Location:** `src/background/messages.ts:297`

**Mechanism.** handleSignHash (src/background/messages.ts:297-306) parses the message and returns `{ ok: true,
signature: await ctx.wallet.signHash(input) }`. readSignHashInput accepts `{accountId?, messageHash,
vaultPassphrase}` and requires only that the hash be a Stark field element and the passphrase pass
isVaultPassphrase.

**Impact.** Unnecessary attack surface on the privileged router. wallet.signHash turns "holds the passphrase"
into "can produce a silent, unaudited signature over any field element" — including a precomputed
transaction hash the user never saw — with no activity trace.

**Remediation (shipped).** Both message types are gone from the router, from the input parsers, and
from the key-boundary catalog; a `wallet.signHash` or `wallet.grantOrigin` message now answers
`unsupported message`. The in-process `WalletVaultService.signHash` behind `accountHashSigner` and the
vault-service `grantOrigin` behind `applyConnect` are untouched, so hash signing stays reachable only
from a reviewed operation and a grant only from a user decision.
`tests/background/callerless-privileged-messages.test.ts` pins the removal and asserts the account key
was never touched on the way to the rejection.

### MCW-V09-125

- **Severity:** Low  |  **Area:** memory  |  **Status:** Resolved
- **Location:** `src/storage/allowance-store.ts:170`

**Mechanism.** record() reads the whole allowance array, filters out the same id, then keeps
`kept.slice(-(MAX_ENTRIES - 1))` before appending — the slice is taken over the GLOBAL list with no
scoping by accountId or networkId (src/storage/allowance-store.ts:164-172, MAX_ENTRIES = 200 at
:25).

**Impact.** The allowance manager reports a false negative on a security control: an account can show "no
allowances" while holding live unlimited approvals, because its records were pushed out by activity
on a different account.

**Remediation (shipped).** Retention is now two bounds, both in `ALLOWANCE_LIMITS`: 50 entries per
account-and-network scope, and 200 across the whole log — the second because every write goes through
`assertJsonValue`, and a log that outgrows that budget stops tracking new grants silently, which is the
same harm as evicting them.

The scoping is stated rather than inherited. `allowanceScope` names the concept, and the record
validator refuses an entry whose `networkId` disagrees with its account id's `<networkId>:<address>`
prefix — so the same address on mainnet and Sepolia can never share a scope, and that is a checked
property rather than an artefact of how account ids happen to be spelled.

The per-scope cap alone only half-closed the finding, and the second half is the interesting one: with
the log full at four saturated scopes, a globally-oldest eviction lets one busy account push another
account's records out one per write until it reports "no allowances" while still holding live unlimited
approvals — the original false negative, reached at a higher threshold. Recency of WRITE is not evidence
that an allowance is dead, so it may decide which of a scope's own records goes and never which scope
goes hungry. `trimToTotal` therefore levels down the fullest scopes: each round takes a slot from every
scope currently holding the most, leaving the survivors within one entry of an equal share. Levelling
the whole tallest row rather than picking a scope by name is deliberate — a tie broken by a fixed rule
sends every eviction to the same unlucky account until it is empty. A freshly granted allowance is
always retained.

`tests/storage/allowance-store-scope-cap.test.ts` pins both caps against both store implementations,
including that a newly busy account cannot empty an idle one and that the surviving scopes hold
comparable shares; `tests/storage/allowance-store-budget.test.ts` pins that the log stays inside the
storage JSON budget and that the grant just made always survives.

### MCW-V09-126

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/sidepanel/runtime.ts:341`

**Mechanism.** loadStatus returns `isWalletStatus(response) ? response : emptyStatus()`
(src/sidepanel/runtime.ts:339-341), and emptyStatus() (:82-92) sets `hasVault: false, locked: true,
ready: false`.

**Impact.** The wallet's fail-closed security control renders to the user as "you have no wallet." A user whose
storage lockdown failed, or who hits a transient preferences-read error, sees a wallet that appears
to have forgotten their accounts and offers to set up a new …

**Remediation (shipped).** The two cases are now two values in
`packages/presentation/wallet-ui/src/sidepanel/runtime/runtime-status.ts`. `emptyStatus()` stays the
pre-load placeholder; a failed or unrecognised `wallet.status` reply paints `unavailableStatus()`,
which reports `hasVault: true, locked: true, ready: false` and a network of "Unavailable". An
unanswered read is not evidence that there is no wallet, so the panel offers the unlock gate with
its submit disabled rather than the first-run journey — a fault state that destroys nothing and
resolves itself the moment a real status arrives.
`packages/presentation/wallet-ui/tests/sidepanel/runtime/status-failure-first-run.test.ts` pins that
a status failure never renders setup.

### MCW-V09-127

- **Severity:** Low  |  **Area:** supply-chain  |  **Status:** Open (partially remediated)
- **Location:** `scripts/check-krusty-adapter.ts:17`

**Mechanism.** scripts/build-extension.ts:186-193 copies vendor/krusty-kms/crates/wasm/pkg/krusty_kms_wasm.js
and krusty_kms_wasm_bg.wasm straight into dist/, and scripts/extension-runtime-files.ts:17-18 admits them to
the zip.

**Impact.** There is no way for a maintainer, reviewer, or downstream user to verify that the crypto core in a
given dist/ or artifacts/*.zip was built from the pinned commit.

**Remediation (partial).** Before importing the package, `check:krusty` requires the checkout to sit on
`KRUSTY_KMS_REVISION` read back out of the vendor script, a clean worktree, a reviewed SHA-256 for the
wasm-bindgen glue (derived from the crate's exported API alone, so it holds on every machine), and
known-answer vectors over a published BIP-39 phrase, pinned by `tests/scripts/krusty-provenance-pin.test.ts`.

**What remains.** `krusty_kms_wasm_bg.wasm`, the core that executes, has no byte provenance. Round 2 pinned
its SHA-256, but `vendor:krusty` compiles that file locally, so its bytes follow the builder's toolchain, not
the pinned source: the literal failed release CI on the first foreign builder and round 3 removed it. The
gate's header records the residual and a test keeps it there — the source pin fixes what may ship and the
vectors catch a core whose behaviour moved, but neither detects a tampered `pkg/`. Krusty KMS is trusted as
first-party until it ships as a pinned npm dependency (**issue #235**).

### MCW-V09-128

- **Severity:** Low  |  **Area:** vault  |  **Status:** Resolved
- **Location:** `src/wallet/vault-service.ts:158`

**Mechanism.** createLedgerVault refuses to run over a non-fresh store — `if (vault.accounts.length > 0 ||
vault.mnemonic !== null) throw new WalletError("Wallet already exists")` (src/wallet/vault-
service.ts:231-233).

**Impact.** Over a v1-migrated vault the wallet's recovery phrase is permanently set to an unrelated phrase that
restores none of the pre-existing accounts, while the reveal screen presents it as the wallet's
phrase — recovery then depends on the encrypted vault surviving …

**Remediation (shipped).** `createAccount` refuses to displace a stored seed: over a keyless vault it
requires no existing accounts, and over a seeded one it requires the same phrase, so onboarding is
first-run-or-idempotent and `addDerivedAccount` owns every later HD account. Both refusals throw
`Wallet already exists`, matching the `createLedgerVault` sibling.
`tests/wallet/vault-service-create-seed-guard.test.ts` pins the v1-migrated case that motivated the
finding.

### MCW-V09-129

- **Severity:** Low  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/starknet/starkscan-wallet.ts:122`

**Mechanism.** defaultRuntimeRpc wires `getTokenBalances: getPreferredBalances` and `getTransactionHistory:
getPreferredHistory` (src/background/runtime-rpc.ts:214,216), built over a hard-coded
https://starkscan.co/v1 client (:192-195) with no preference switch.

**Impact.** Three consequences. (1) Two sources of truth: with an rpcOverride configured, the panel displays
balances and activity from starkscan.co while every transfer, fee estimate, and submission goes to
the override — displayed state and transacted state can diverge …

**Remediation (shipped).** Two parts, in two rounds.

*Trust ordering.* `createRpcFirstBalances` and `createRpcFirstHistory` serve from the user's
configured Starknet RPC and reach the explorer gateway only when every configured endpoint has
failed, and a gateway failure re-throws the RPC failure so the third party can never explain away
the user's own endpoint. That removed the two-sources-of-truth divergence and the per-refresh
address disclosure. `tests/starknet/starkscan-rpc-first.test.ts` pins the ordering as a trace, not
just as a count.

*Opt-in.* The lane is now permitted per network by an `explorerFallback` preference
(`src/storage/preferences-entries.ts`), resolved by `explorerFallbackAllowed`: an explicit stored
choice always wins, and with none the default is derived from the user's own configuration — on for
a user on the built-in RPCs (no behaviour change for them), off for any network with an
`rpcOverride`, because configuring your own endpoint reads as a decision that no third party should
see your addresses. Such a user gets the RPC failure on an outage instead of a silent disclosure and
can turn the lane back on under Settings → Network → Advanced endpoints → Explorer fallback
(`packages/presentation/wallet-ui/src/sidepanel/journeys/settings/network-views.ts`, bound in
`packages/presentation/wallet-ui/src/sidepanel/journeys/settings/endpoint-ui.ts` through the
privileged `wallet.setExplorerFallback` message). The background builds its read adapters from the
real preferences reader (`createDefaultRuntimeRpc` in `src/background/runtime-rpc.ts`), and the gate
fails closed: an unidentifiable network or a preferences read that throws leaves the gateway
untouched. `explorerFallback` is excluded from `pickImportablePreferences`, so a backup file can
neither arm nor disarm the lane. No preferences migration was required — the field is optional and
its absence means "never decided", which the resolver answers from `rpcOverrides`.

`tests/starknet/starkscan-explorer-lane.test.ts` pins both defaults and both explicit overrides for
balances and history against a gateway that records every URL it is asked for;
`tests/storage/preferences-explorer-fallback.test.ts` pins the resolver, the validator, the store
mutation, a record written before the field existed, and the backup exclusion; and
`packages/presentation/wallet-ui/tests/sidepanel/journeys/settings/explorer-fallback-settings.test.ts`
pins that the control renders the state the background would apply and submits the box's literal
value.
