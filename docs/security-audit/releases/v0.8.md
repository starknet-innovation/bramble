# v0.8 on-chain NFT animation rendering — security design

| Field | Value |
| --- | --- |
| Runtime scope baseline | unreleased (branch `feat/nft-animation-url`) |
| Release | `v0.8.0` (not cut) |
| Status | **Independent security review complete — browser regression hardening included** |
| Open findings in reviewed scope | 0 known |

> This document records the threat model, mitigations, and browser-level verification for the
> feature. Independent review added an adversarial self-navigation probe and a second sandbox on
> each embedding iframe. The probe confirms that a hostile animation cannot reach the network;
> the embedding sandbox preserves the opaque-origin boundary if it replaces its own document.

## Feature

Some fully-on-chain collectibles (e.g. Game of Life `gol_metadata_v2` lifeforms) expose their art
as an `animation_url` = `data:text/html;base64,…` — an HTML page whose inline `<script>` animates a
`<canvas>`. Such tokens carry no static `image`, so the v0.7 image path shows only a placeholder.
This feature renders that untrusted HTML, on explicit user action, inside an isolated sandbox.

## Security model — two independent boundaries

1. **Code isolation.** The HTML runs only inside `sandbox/render.html`, declared in the manifest
   `sandbox.pages`. Chrome executes this page in an isolated security principal. Browser E2E
   checks verify that the untrusted script has no `chrome.runtime` or `chrome.storage` access and
   cannot read or mutate the parent (side-panel) DOM, so it cannot reach the vault, background
   service worker, or extension storage. A generic `chrome` object may still exist and the
   location may serialize as a `chrome-extension://` URL; neither is treated as a security
   boundary.
2. **Network egress.** The `sandbox`/`allow-scripts` attribute does *not* block `fetch`,
   WebSocket, `sendBeacon`, or remote `<img>`. Egress is blocked by the page's own CSP
   (`content_security_policy.sandbox`): `default-src 'none'` (no `connect-src`, no `frame-src`) plus
   `img-src data:` only. Each embedding iframe independently repeats `sandbox="allow-scripts"` and
   sets `referrerpolicy="no-referrer"`, preserving the opaque-origin boundary across a hostile
   self-navigation attempt. Browser E2E verifies that fetch, images, and that navigation reach no
   network server. An opened collectible therefore cannot phone home and correlate the viewer's IP
   with the wallet address — consistent with the existing v0.7 anti-tracking boundary.

## Reviewed trust boundaries

- Contract `token_uri` JSON `animation_url` → `normalizeAnimationUri` (only `data:text/html`,
  size-capped, verbatim) → `isDiscoveredNft` round-trip re-validation at the background boundary.
- Watched-only resolution: `animation_url` is resolved only for explicitly watched tokens, never
  for unsolicited indexer candidates (inherits the v0.7 reveal boundary).
- Side panel → sandbox page: the URI is passed via the **iframe URL hash**, not `postMessage`, so
  the privileged side panel adds no window-message listener and the isolated frame has no channel
  back into privileged logic.
- Sandbox page: reads its own `location.hash`, decodes via a pure, unit-tested
  `decodeHtmlDataUri`, and `document.write`s the HTML into itself so the inline script runs under
  the manifest sandbox + egress-blocking CSP. `document.write` is intentional here: assigning the
  payload through `innerHTML` would not execute inserted script elements and would break the
  supported animation. The sink is restricted to this standards-allowlisted sandbox entrypoint.
  Malformed input fails closed to a short message.
- Reveal consent: nothing loads until the user presses "Play" on the detail view (no gallery-grid
  animation, no auto-play).

## Residual boundaries and risks

- **Renderer parser exposure.** Rendering any attacker-controlled content exposes the browser
  engine; a locked-down canvas is comparable to the existing static-SVG image path. Accepted.
- **Browser-enforced boundary.** Isolation and egress restrictions ultimately depend on Chrome's
  manifest-sandbox and CSP implementation. The E2E suite exercises these properties in Chromium;
  future browser/manifest changes must keep that test green.
- **Animation resource use.** A self-contained animation can consume CPU while its detail view is
  open. It receives no wallet data and navigation destroys the frame, but browser renderer
  resource exhaustion remains a residual availability risk.
- **Scope.** Only self-contained `data:text/html` is accepted; remote (`https`/`ipfs`) and other
  animation media types are rejected to keep the no-egress guarantee simple.

## Validation performed by the implementer

- `bun run check` (types, Biome, file/config standards including the new manifest sandbox CSP pin
  and the hardened HTML-sink pattern, import layers, cycles, extension manifest, Krusty and
  multisig pins, and the unit/integration suite).
- `bun run build`: reproducible `dist/` including `sandbox/render.html` + `sandbox/render.js`.
- Unit tests: `normalizeAnimationUri`, `isDiscoveredNft` animation acceptance/rejection,
  `metadataFromJson` reading a real `gol_metadata_v2`-shaped `token_uri`, the background enrich
  merge, `decodeHtmlDataUri`, and the Play-button reveal binding.
- Playwright browser proof: a fixture animation executes inside the real built extension sandbox;
  `chrome.runtime` and `chrome.storage` are unavailable; parent-DOM access is rejected; `fetch`, a
  remote `<img>`, and an attempted self-navigation make zero requests to a local probe server; and
  a malformed data URI fails closed. A separate accepted static-SVG fixture
  renders through `<img>` without executing its script or requesting its remote image subresource.

Independent review disposition: no open security finding remains in this feature scope.
