# v0.10.1 preliminary scope review

Private working report. No public disclosure or deployment is performed by this review.

## Baseline and method

Requested scope: the "Starknet Wallet – Preliminary Security Audit Scope" outline
(architecture/trust boundaries, key management and cryptography, Starknet account and
signing logic, transaction security, dapp connectivity, authentication/session,
authorization/API, client-side security, Starknet-specific scenarios, asset/token
handling, network/RPC, supply chain, business logic).

Baseline reviewed: `41ad4f8353c2171e7a94092968768442db8a450c` (`main`, released as
v0.10.1). This is the exact merge-base of `hotfix/v0.10.1-security-audit`: the hotfix
branch adds the ten [v0.10.1 audit](v0.10.1-audit.md) remediation commits (none of
`05df6142`, `954094ae`, `3caf6cab`, `31abd8db`, `65070d84`, `3d397e17`, `75f06fcb`,
`7c2e70f5` are ancestors of `main`) on top of the reviewed tree. Every finding whose
implicated files changed on the hotfix branch was re-verified against the hotfix head
`39598eec5887ca9b3b8661836ba264f34ca22296` and is marked "re-verified" below; all
other findings implicate files identical between the two trees. Soundness claims are
stated against the hotfix tree, where this report ships; the hotfix-only claim-time
session binding (`approval-session.ts`, wired at `approval-decisions.ts:408`) was
verified directly there.

Method: eight parallel domain reviews with entry-point enumeration, manual
trust-boundary tracing, and call-graph following; every reported finding was
independently re-confirmed by reading the implicated code. This is a source review,
not a certification; dependency internals, deployed contracts, and operator
infrastructure remain external trust dependencies per the v0.10.1 audit's stated
limits.

Items already documented in the v0.10.1 audit or its threat model are marked
"previously acknowledged" and restated only where this review adds mechanics or a
concrete residual.

## Principal findings

### P-01 — SNIP-12 typed-data signatures are not bound to the active network (High)

`apps/extension/src/background/transactions/chain-ops.ts:124` (execution) and
`chain-ops.ts:190` (queue time) compute the hash as
`typedDataHash(input.typedData, account.address)`. The hash binds the account address
but never the network. `isSupportedDomain`
(`packages/platform/starknet/src/transactions/typed-data.ts:235`) requires only that
every domain key be declared in the dapp's own domain struct; it neither requires a
`chainId` key nor compares one against
`STARKNET_NETWORKS[account.networkId].chainId`.

`deriveNetworkAccount`
(`packages/platform/vault/src/accounts/network-account.ts:47`) projects one wallet key
onto every network with a network-independent address (class + `publicKeyX` + salt; no
chain input), so the same address controlled by the same key exists on mainnet and
Sepolia. A page connected on Sepolia can therefore request a signature whose domain
declares `chainId: "0x534e5f4d41494e"` (`SN_MAIN`) — or whose domain struct omits
`chainId` entirely, producing a chain-agnostic signature — and replay it on mainnet
against any verifier that accepts it. The wallet's own paymaster flow
(`packages/features/privacy/src/paymaster/paymaster-typed-data.ts`) demonstrates that
the deployed account class honors SNIP-9 `OutsideExecution`, so a concrete payload is a
mainnet `execute_from_outside` authorization harvested from a "sign to log in" prompt
on Sepolia.

Every transaction path hard-binds the chain (write endpoints are selected by
`starknet_chainId` probe and the probed value feeds the signed hash; multisig intents
freeze `chainId` into the prepared hash and re-verify it). Typed data is the one
unbound signing surface.

Partial mitigations: the sign card decodes and displays the declared domain as signed
rows (`packages/presentation/wallet-ui/src/sidepanel/shared/sign-request.ts:139`), and
the phishing blocklist gates the origin. But nothing refuses or warns on a foreign or
absent chain id, and a hex-spelled `0x534e5f4d41494e` row is not obviously "mainnet"
to a user on Sepolia.

Recommended direction: require the domain to declare `chainId` and refuse (or loudly
warn) when it does not felt-equal the active network's chain id; consider a prominent
capability warning for `OutsideExecution`-shaped payloads (P-36).

Confidence: confirmed at code level on both baselines. End-to-end exploitability
against a specific live verifier is needs-runtime-verification.

### P-02 — No throttling on the unlock oracle (Medium; previously acknowledged)

`handleUnlock` (`apps/extension/src/background/routing/messages.ts:261-289`),
`handleRevealSecrets` (`messages.ts:115-127`), and the passphrase-carrying form of
`handleGetGrantedAccounts` (`messages.ts:128-154`) each permit unlimited attempts; the
only brake is one PBKDF2-SHA-256 derivation (600,000 iterations,
`packages/platform/vault/src/encrypted-store.ts:11`) per guess, and the wrong-passphrase
response is a clean binary oracle. A repo-wide search confirms no throttle, counter, or
lockout exists on any auth path. All three messages are privileged and unreachable from
dapps/content scripts (deny-by-default gating in `routing/senders.ts`), so the
practical surface is an attacker with extension-page code execution, or offline attack
against the ciphertext — which the KDF parameters address. The v0.10.1 audit already
records "no durable password-attempt lockout"; this review re-confirms the mechanics
and notes the oracle is also reachable via `wallet.getGrantedAccounts` with a
message-supplied passphrase.

### P-03 — Read lane is single-endpoint trust (Medium; threat-model acknowledged)

`mergeActivity` (`packages/features/transactions/src/history/tx-history.ts:253-266`)
reconciles a locally recorded pending transaction to `accepted` purely because the
node's event stream contained a matching `Transfer` event, and injects on-chain rows
with no local counterpart directly into the activity feed. Reads go through
`withRpcFallback` (`packages/platform/starknet/src/rpc/provider.ts:275-305`), which
fails over only on transport errors: the first available endpoint has a monopoly on
semantic answers, and no read path verifies chain id or cross-checks a second
endpoint. An endpoint that relayed the user's transaction (and therefore knows its
hash) can mark an unrelayed transaction accepted, inject fake inbound-transfer rows
(a classic payment-deception pattern), or report arbitrary balances. Impact is
display-integrity, not direct fund loss: signing is chain-id-gated and hash-matched,
and the endpoint cannot move funds. The threat model already accepts that chain-id
probes do not prove authentic chain state; this review traces the concrete mechanics.
A cross-endpoint quorum for status/history, or at least for reconciling local pending
transactions, would close the deception vector.

## Selected Low findings

- **P-04** — `handleGetGrantedAccounts` returns `{ error: "wallet locked" }` when
  locked but `{ accounts: [], ok: true }` when unlocked-and-unconnected
  (`messages.ts:148-153`), while sibling probes (`wallet_getPermissions`, silent
  `wallet_requestAccounts`) deliberately return indistinguishable empty results in both
  states. Any website can passively learn whether the wallet is currently unlocked —
  useful for timing phishing prompts.
- **P-06** — `openApprovalSurface` runs synchronously on every runtime message
  (`apps/extension/src/background/index.ts:407-409`) and gates only on message type,
  blocklist, and a 1-second per-tab cooldown
  (`apps/extension/src/background/approvals/approval-surface.ts:63-77`). A page can
  force-open the side panel once per second with payloads that will be rejected. No
  consent can be forged; the residual is UI spam. A cheap payload-parse gate before
  raising the surface would eliminate most of it.
- **P-07** — The dapp invoke card renders decoded summaries with addresses truncated
  to 4+4 hex characters (`packages/features/transactions/src/routing/verify-decode.ts`
  `shortAddress`) and offers no full-address or raw-calldata inspection, unlike the
  STRK20 card's "Exact action parameters" disclosure. The address-poisoning refusal
  covers only lookalikes of saved addresses, so an unsaved recipient is unverifiable at
  the decision point within a grindable 32-bit window.
- **P-08** — ERC20 `approve(spender, amount)` and ERC721 `approve(to, tokenId)` share
  selector and shape; disambiguation relies on `isWatchedNftContract`
  (`verify-decode.ts:336-371`). For an unwatched collection, an NFT approval displays
  as "spend N units". The unknown-contract risk flag fires alongside, bounding impact.
- **P-10** — `swapConfirmReceipt`
  (`packages/presentation/wallet-ui/src/sidepanel/journeys/swap/swap-views.ts:176,180`)
  interpolates symbols and amounts raw into markup assigned to `innerHTML`; every
  sibling renderer escapes. Not exploitable today — symbols are validated by
  `isTokenSymbol` at every write/read boundary — but `SwapCatalogTokenView` validates
  symbols with only `length > 0`, so wiring catalog-supplied symbols into this receipt
  would become stored XSS in the privileged side panel.
- **P-11** — The pending-registration dedup guard matches activity entries on the exact
  summary `"Activate private balances"`
  (`apps/extension/src/background/privacy/strk20-wallet-ops.ts:74-88`), but a
  dapp-initiated registration records `"${origin} submitted N calls"`
  (`apps/extension/src/background/provider/provider-ops.ts:438-441`). During the
  indexer lag window either direction can prepare a redundant registration; the user
  pays gas twice. No key or funds exposure.
- **P-15** — Submission-time re-estimation refuses spend above the reviewed figure
  +50% and signs exactly the checked bounds (`rpc-submit.ts:96-122`), closing the
  inflation direction. But both estimates come from the same endpoint: a malicious RPC
  can consistently lowball, so the user reviews a cheap fee and the transaction reverts
  out-of-gas while still charging the consumed fee. Bounded by the reviewed absolute
  amount. No sanity floor or cross-endpoint estimate comparison exists.

## Areas verified sound

This review re-traced the following boundaries and found them holding; the v0.10.1
audit remediations (V0101-01 through V0101-10) are present on the hotfix head.

- **KMS boundary.** Krusty owns all wallet crypto; no fallback signing, key
  derivation, or mnemonic validation exists. The adapter validates every input/output
  and enforces the signing-scalar rule; raw-key import recovers the public key via a
  Krusty probe signature rather than local derivation; the starknet.js `Signer` is
  constructed with a dummy key whose `signRaw` is fully overridden. The published KMS
  package is pinned exact with SHA-256 digests of both runtime files plus
  known-answer vectors (`scripts/check-krusty-adapter.ts`).
- **Vault cipher.** PBKDF2-SHA-256 600k, AES-256-GCM with per-write salt/IV,
  scope+lineage+commit bound as AAD, tampered iteration counts rejected, legacy
  envelopes transparently re-encrypted, non-extractable key cache dropped on lock,
  rollback rejected via independent commit markers.
- **Secret egress.** The key-boundary suite scans every handled message's serialized
  response for secret material; there is deliberately no `wallet.signHash` or
  `wallet.grantOrigin`; `wallet.revealSecrets` requires passphrase re-entry; event
  broadcasts carry no addresses or secrets; raw error messages reach extension pages
  only. Analytics emit only a random installation id plus bounded version/platform
  headers to the exact gateway origin, with consent recheck and redirect refusal.
- **Approve-hash-A-sign-hash-B resistance.** Approval payloads are deep-cloned and
  SHA-256 digest-bound at queue time and re-verified at claim; claims are synchronous
  and single-use; the UI's echoed fee must exactly match the queue's current figure;
  the displayed fee is the enforced signing ceiling with +50% submission headroom;
  accepted broadcast hashes must equal the exact signed hash.
- **Session revocation.** Generation-bound session authorization is re-checked before
  and after awaited work on every signing and mutation path; lock drops derived-key
  caches, revokes in-flight Ledger requests, and refuses to report "locked" until the
  session-mirror erase is proven; dapp/polling paths use non-renewing peeks so no page
  cadence can hold the wallet unlocked.
- **Dapp perimeter.** Deny-by-default privileged gating with browser-supplied sender
  evidence; the dapp-reachable allowlist is enforcement-tested as derived from the
  bridge sources; grants are exact-origin with no subdomain widening and reveal at
  most the active account; every execution path re-resolves the grant at execution
  time; queue caps, TTLs, and waiter release bound consent-surface flooding.
- **Multisig integrity.** Prepared intents recompute execute calldata and the V3 hash
  from frozen fields and require equality; co-signer signatures are verified against
  the exact hash and signer set; config/nonce drift marks intents stale; Nostr
  coordination re-derives and re-reviews imported intents.
- **Privacy/paymaster binding.** Prepared proofs may only ride the configured pool's
  `apply_actions` as the last call with `approve`-only prefixes; relay SNIP-9 typed
  data is reconstructed wallet-side and accepted only on hash equality; the relay fee
  must equal the independently read on-chain pool fee.
- **Client-side hygiene.** The string-HTML sink whitelist is enforced by gate and was
  independently verified; `escapeHtml` covers text and quoted-attribute contexts; no
  wildcard `postMessage` targets exist; both bridge listeners check source and origin;
  no `localStorage`/`indexedDB` in production code; storage areas are locked to
  trusted contexts at startup with fail-closed boot; clipboard is write-only behind
  user clicks; NFT HTML runs in an opaque nested sandbox.
- **Supply chain.** All dependencies exact-pinned with lockfile integrity; vendor
  scripts verify HEAD, worktree cleanliness, and SHA-256 artifact digests and
  recompute class hashes; CI workflows are SHA-pinned with a fail-closed policy gate;
  the release pipeline re-verifies the zip checksum before publish; no embedded
  secrets found; updates are Chrome Web Store only with no self-update code.

## Limitations

- Source review only: no dynamic exploitation was attempted against live verifiers,
  and P-01's end-to-end replay against a specific mainnet verifier is marked
  needs-runtime-verification accordingly.
- Dependency internals (starknet.js, KMS WASM, privacy SDK), deployed account/pool
  contracts, Ledger firmware, and operator infrastructure (gateway/paymaster firewall,
  analytics retention) remain external trust dependencies, unchanged from the v0.10.1
  audit's stated limits.
- `check:argent`/`check:privacy` vendor gates require network access and were not
  re-run in this sandbox; the vendored outputs were reviewed as present.
