# Starknet Wallet – Preliminary Security Audit Scope

- Baseline: `41ad4f8353c2171e7a94092968768442db8a450c` (`main`, released as `v0.10.1`).
- Audit branch: `audit/v0.10.1-security`.
- Started: 2026-09-09.
- Status: scope recorded; audit execution and findings are pending.

## Wallet architecture & trust boundaries

- Client/backend architecture
- Browser extension/mobile components, if applicable
- RPC/provider dependencies
- External APIs and third-party integrations
- Privileged/backend services and trust assumptions

## Key management & cryptography

- Private key generation, storage and lifecycle
- Seed phrase / recovery mechanisms
- Secure enclave/keychain usage where applicable
- Key import/export
- Encryption of locally stored secrets
- Signing implementation and cryptographic misuse
- Prevention of sensitive material leakage through logs, telemetry, backups, etc.

## Starknet account & signing logic

- Account abstraction implementation
- Account deployment flows
- Transaction construction and signing
- Nonce handling and replay protection
- Chain ID / network validation
- Typed-data signing / SNIP-12 flows
- Signature validation assumptions
- Fee estimation and transaction simulation
- Multicall/batched transaction handling

## Transaction security

- Verification of transaction destination, calldata and value
- User confirmation screens vs. actually signed payload
- Transaction tampering
- Malicious calldata / deceptive transaction scenarios
- Approval and token-transfer flows
- Contract deployment / upgrade interactions
- Signing of arbitrary messages and potentially dangerous signatures

## DApp / Wallet connectivity

- Wallet connection and permission model
- Origin/domain validation
- DApp authorization lifecycle
- Cross-origin messaging
- Malicious website scenarios
- Permission escalation between connected applications
- Account/network switching
- Session persistence and revocation

## Authentication & session management

- Wallet unlock mechanisms
- Password/PIN controls
- Brute-force protections
- Session timeout/locking
- Authentication bypass
- Device/session management if a backend account exists
- Recovery/account takeover scenarios

## Authorization & API security

- IDOR/BOLA/BFLA
- Privilege escalation
- Authentication bypass
- API token/session handling
- Rate limiting
- Input validation
- Business-logic abuse
- Sensitive information exposure

## Client-side security

- XSS / HTML injection
- DOM-based attacks
- Extension message-passing security
- Content-script isolation
- CSP and browser security controls
- Deep-link / custom URL handling for mobile
- Clipboard-related risks
- Local storage / IndexedDB exposure

## Evidence and coverage tracking

For each scoped area, record reviewed components, trust assumptions, concrete evidence,
verification performed, findings, and remaining coverage. Mark conditional components
not applicable only after checking the architecture. Distinguish externally operated
services whose implementation is unavailable from client-side integration coverage.
Historical audit reports are context, not evidence that this baseline is secure.
