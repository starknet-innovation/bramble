# v0.9 deep audit — low findings

Continuation of the [v0.9 deep adversarial audit](../v0.9-deep/). Method, verification, and
residual boundaries are defined in the parent document.

### MCW-V09-112

- **Severity:** Low  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/sidepanel/swap-ui.ts:399`

**Mechanism.** The review handler sends `buyAmount: compactAmount(quoted.buyAmount)` (src/sidepanel/swap-
ui.ts:399). compactAmount is the display formatter: it applies groupThousands (src/sidepanel/token-
row.ts:42, `whole.replace(/\B(?=(\d{3})+(?!\d))/g, ",")`) and, for sub-unit values below the 8-place
floor, returns the literal string `<0.00 …

**Impact.** wallet.swapPrepare returns `{error: "invalid swap preparation request"}` and the panel shows "Could
not prepare a safe swap route." The user can never reach the confirmation step.

**Remediation (shipped).** The review message carries the raw machine value (`buyAmount:
quoted.buyAmount`, already `formatTokenAmount` output, which matches `isTransferAmount` by
construction) and `compactAmount` is applied only at render time.
`tests/sidepanel/swap-large-amount.test.ts` drives a quote above the grouping threshold through the
real handler, so the separator can never come back.

### MCW-V09-113

- **Severity:** Low  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/background/wallet-ops.ts:348`

**Mechanism.** handleLock revokes exactly one class of in-flight authority:
`deps.ledgerSignQueue?.rejectAll("wallet locked"); deps.session.lock();` (src/background/wallet-
ops.ts:346-350). The vault-signing sibling has no equivalent.

**Impact.** A user who hits Lock during the RPC window of a transaction they have just authorized — the natural
reaction to realising a site is malicious, or to a review screen showing something unexpected — does
not stop it.

**Remediation (shipped).** The guard lives at the signing seam, expressed once. `captureSessionAuthorization`
(`src/background/session.ts`) records the generation and secret an operation was authorized under and
answers one question — is that unlock still the current one — so no caller compares generations and
passphrases by hand. `accountHashSigner` captures it when the signer is built and re-checks it both
before the vault is touched and again before the signature is handed back, so a lock during the RPC
window rejects with `wallet locked` and never returns a usable signature. `AccountHashSignerDeps.session`
is required, not optional: forgetting it is a compile error rather than a signer that fails open.
Resolving it in totality meant covering the privacy product line too, which the first pass missed —
`strk20AccountContext` built its signer with no session at all, so an extension-owned private transfer
kept signing after Lock. It now requires the session and routes through the same
`accountHashSigner`. `tests/background/vault-sign-lock-revocation.test.ts` and
`tests/background/strk20-vault-sign-lock-revocation.test.ts` pin both, including the case where the
vault answers but the user locks before the signature comes back.

### MCW-V09-114

- **Severity:** Low  |  **Area:** vault  |  **Status:** Resolved
- **Location:** `src/background/session.ts:103`

**Mechanism.** clear() issues `void store?.clear().catch(() => undefined)` — the removal of the plaintext
passphrase mirror from chrome.storage.session is never awaited, never verified, and never retried,
while the in-memory state is nulled synchronously and the generation is bumped.

**Impact.** An explicit user lock — the one control a user reaches for when handing over the machine or stepping
away — can fail open. The vault comes back unlocked with the full passphrase restored from storage,
and every dapp-facing surface resumes signing eligibility, …

**Remediation (shipped).** The erase is proven, not issued. `eraseMirror` removes, retries once, and
failing that overwrites the entry with a `{revoked: true}` marker `restore()` refuses — durable, so the
next MV3 worker cannot resurrect the session either; only if all three fail does `mirrorCleared()`
reject, and `handleLock` awaits it and answers `wallet lock incomplete` rather than a locked status,
because reporting "locked" is a security claim. Mirror writes run on one serial queue tagged with the
session generation, so a save in flight when the user locks cannot land after the erase.
`tests/background/lock-mirror-clear-failure.test.ts` pins all three outcomes.

### MCW-V09-115

- **Severity:** Low  |  **Area:** memory  |  **Status:** Resolved
- **Location:** `src/background/signature-waiters.ts:32`

**Mechanism.** register(id) appends to a per-id resolver array with no cap, no TTL, and an O(n) spread copy per
call: `waiters.set(id, [...(waiters.get(id) ?? []), resolve])` (src/background/signature-
waiters.ts:32).

**Impact.** Unbounded heap growth plus quadratic CPU inside the MV3 service worker — the process holding the
unlock passphrase, the approval queue, and every held dapp promise — driven remotely with no
preconditions.

**Remediation (shipped).** `register` refuses past `MAX_WAITERS_PER_APPROVAL` (8, which covers the
multi-tab case the module exists for) with the same `Too many pending approvals` shape the queue-full
path already uses, and `pending()` counts held responses rather than ids so the number reported is the
memory actually held. `tests/background/signature-waiter-bounds.test.ts` pins the cap and that
settling frees the slots.

### MCW-V09-116

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/background/approvals.ts:279`

**Mechanism.** enqueue enforces only a global cap — `if (pending.size >= MAX_PENDING_APPROVALS) { throw new
WalletError("Too many pending approvals"); }` (src/background/approvals.ts:278-281,
MAX_PENDING_APPROVALS = 50 at :33).

**Impact.** Denial of the wallet's entire consent surface by an unauthenticated origin, plus a UI takeover:
dashboard renders approvalTakeover whenever any un-snoozed approval exists
(src/sidepanel/views.ts:331-335), so the user cannot reach Send, Activity, Settings, or t …

**Remediation (shipped).** Both bounds live in `src/background/approval-limits.ts`:
`MAX_PENDING_APPROVALS_PER_ORIGIN` (5) is checked inside `enqueue` alongside the global 50, and
`APPROVAL_TTL_MS` (5 minutes) expires an unanswered prompt. Expiry is swept lazily on every queue read
and write — no timer runs in a worker Chrome evicts — and a held dapp response is settled as
`EXPIRED_APPROVAL_RESPONSE`, the string that maps to the spec's USER_REFUSED_OP, so an abandoned queue
drains itself instead of hanging the honest site queued behind it.
`tests/background/approval-queue-bounds.test.ts` and `approval-expiry-waiter-release.test.ts` pin both.

### MCW-V09-117

- **Severity:** Low  |  **Area:** origin-trust  |  **Status:** Resolved
- **Location:** `src/background/index.ts:475`

**Mechanism.** The onMessage listener calls `requestApprovalSurface(extensionApi, approvalSurfacePreference,
runtime.id, message, sender)` synchronously as its first statement
(src/background/index.ts:474-476), before `runtimeReady`, before handleMessage, and therefore before
parseGatedMessage and before every handler's blocklist check.

**Impact.** An origin on the phishing blocklist — whose every request is refused downstream with "origin
blocked" — can still make the genuine MC Wallet side panel or action popup appear on demand, on one
click anywhere on its page.

**Remediation (shipped).** The opener is a constructed closure (`createApprovalSurfaceOpener`) holding
the origin guard, the extension id, a clock, and the surface preference, and it applies the blocklist
before opening anything. The activation constraint is untouched: `sender.origin` is available
synchronously and the blocklist is a pure in-memory read. It fails closed on a sender the browser gave
no origin for, and a one-second per-tab cooldown stops a page holding the wallet UI open in a loop.
`tests/background/approval-surface-origin-gating.test.ts` pins the refusal and the cooldown.

**Mechanism.** handleStrk20SubaccountCommitment takes dappName straight from the dapp's params —
readStrk20SubaccountMessage validates only isStrk20DappName (a felt or <=31 printable ASCII bytes)
and never compares it to input.origin (src/background/strk20-provider-inputs.ts:100-116).

**Impact.** Two origins naming the same dappName receive byte-identical commitments, so any site can obtain the

### MCW-V09-119

- **Severity:** Low  |  **Area:** origin-trust  |  **Status:** Resolved
- **Location:** `src/starknet/rpc-submit.ts:74`

**Mechanism.** The approval card renders "Estimated fee: X" from the queue entry's `fee` field, produced by
estimateInvokeApprovalFee at queue time and replaceable later by updateInvokeFee
(approvals.ts:463-477).

**Impact.** The fee the user reviewed and consented to is advisory only. Between the estimate and the approval
click the true bound can rise without limit — most concretely when the target contract's gas cost
depends on state the requesting dapp controls and flips while t …

**Remediation (shipped).** The reviewed figure now travels into the submission and constrains it.
`submitInvokeTransaction` and `submitDeclareTransaction` take an optional `reviewedFee`; when it is
present they take ONE estimate, build the resource bounds that speed will sign, refuse before anything
is signed or broadcast if the spend THOSE BOUNDS authorise has outrun `REVIEWED_FEE_HEADROOM` (3/2, in
`src/starknet/fee-bounds.ts`), and then pass exactly those bounds — so the ceiling holds over the
transaction that actually goes out rather than over a quote starknet.js takes for itself a moment
later. The headroom is stated rather than assumed: it absorbs ordinary gas-price drift and the
`__validate__` cost the review's `skipValidate` estimate omits, and it is what turns an unbounded rise
into a bounded one.

What is compared matters as much as that something is. A `fast` send scales BOTH bound dimensions by
3/2, so it authorises 2.25x the estimate it was scaled from; checking the headline figure and then
scaling would have let a fast send sign for 3.375x a reviewed fee while reporting itself bound. The
comparison is therefore always against `feeBoundsMaxSpend` of the bounds about to be signed, and the
review is priced for the same speed (`reviewedSpendFor`, threaded through `estimateInvokeFee` and
`wallet.reviewTransfer`) so the figure on the screen is the figure enforced. A bounds mapping that
cannot be read in full refuses rather than falling back to the headline number.

The seam was the whole difficulty, and the reason a first pass left this open: a ceiling parameter no
caller sets enforces nothing. It is now set by every path that shows a user a fee. The dapp invoke and
declare approvals hold the figure themselves — `approval.fee` and `approval.declaration.fee`, which is
what the card is showing at the moment of the click, including after a retry. The panel journeys review
in one message and send in another, so they echo the displayed estimate back on the send
(`wallet.transfer`, `wallet.transferNft`, `wallet.confirmMultisigProposal`), validated at the boundary
by `isFeeEstimate` — the same predicate the pages use to accept a fee for rendering, so a fee one side
draws can never be a fee the other silently drops. Where no fee was reviewed (an estimate that failed,
an internal submission with no review step) the field is absent and the submission stays bounded only
by the node: an invented ceiling would be worse than an honest absence.

Two surfaces beyond the invoke needed the same treatment. The declare card totals a declaration fee
AND an account-deployment fee, and approving submits the deployment first: `ensureAccountDeployed` now
takes the reviewed deployment fee and binds that transaction identically, so both halves of the
displayed total are enforced. The swap card is the opposite answer — `gasFeesInUsd` is the
aggregator's own USD guess, not a wallet-computed resource bound, and nothing signs against it — so
rather than claim an assurance that is not there, the row now reads "Aggregator fee estimate … (not
wallet-enforced)".

`tests/starknet/rpc-submit-fee-bounds.test.ts` pins the enforcement, including that nothing is
broadcast when a submission is refused and that a fast send reviewed at the node's own quote is
refused; `tests/starknet/fee-bounds.test.ts` pins the arithmetic, in particular that every "cannot
compare" case answers *refuse*; `tests/starknet/starknet-deployment-ops.test.ts` pins the deployment
ceiling; and `tests/background/reviewed-fee-binding.test.ts` pins the wiring per surface, which is the
part that was missing. `isBaseUnitsAmount` also gained a 78-digit bound (`src/shared/json.ts`), so no
untrusted caller decides how much `BigInt()` work a fee comparison does.

### MCW-V09-120

- **Severity:** Low  |  **Area:** consistency  |  **Status:** Resolved
- **Location:** `src/background/declare-ops.ts:272`

**Mechanism.** executeDeclareApproval submits via runtimeRpc.submitDeclareTransaction and returns `{ classHash, ok:
true, transactionHash }` (src/background/declare-ops.ts:264-272) without calling activity.record.
Its DeclareExecuteDeps type (declare-ops.ts:48-58) has no `activity` member, so it structurally
cannot record.

**Impact.** A user-approved, fee-paying on-chain declare leaves no local trace: absent from the activity feed
and CSV export, never followed to acceptance or revert, and a rejected or reverted declare produces
no failure notice.

**Remediation (shipped).** `DeclareExecuteDeps` carries the activity log, `applyDeclare`
(`src/background/approval-decisions.ts`) passes it, and a submitted declare is recorded against the
signing account and network with the deterministic summary `Declare contract class 0x…` — so the
background monitor follows it to acceptance or revert like every other submission. Nothing is recorded
when the submission fails, and a failing activity write still reports success, because the declare is
already on chain once the node answers.

The kind was widened to `"declare"` rather than reusing `"invoke"`. A declare and a call are different
transaction types on chain, and the feed and CSV export are what a user reads back when reconciling
what their wallet did; a kind that lies makes the export wrong in exactly the situation it exists for.
The widening needs no stored-schema migration, and this is why: the activity log is not the versioned
vault schema — `CURRENT_SCHEMA_VERSION` and `VAULT_MIGRATIONS` are untouched — but an unversioned local
log that revalidates every row on read and drops what does not validate. Widening an accepted-value set
is therefore purely additive. `tests/storage/activity-declare-kind.test.ts` pins the three cases that
claim rests on (rows written before the change still validate, a declare row round-trips through the
store and its CSV export, an unrecognized kind is still refused), and
`tests/background/declare-activity-record.test.ts` pins the recording, including that its summary
matches neither multisig dedup guard.

### MCW-V09-121

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/starknet/provider.ts:41`

**Mechanism.** createRpcProvider (src/starknet/provider.ts:41-45) passes only `{...options, nodeUrl, specVersion}`
and never sets baseFetch, so starknet.js falls back to a bare fetch with no AbortSignal.

**Impact.** The multi-endpoint failover the network config is built around is inert against the most common real

**Remediation (shipped).** `createRpcProvider` sets `baseFetch: timedRpcFetch()` itself, so every

fails if any module outside `provider.ts` builds a provider transport of its own.
`tests/starknet/rpc-provider-timeout.test.ts` pins that a black-holed endpoint aborts and fails over.

### MCW-V09-122

- **Severity:** Low  |  **Area:** availability  |  **Status:** Resolved
- **Location:** `src/background/index.ts:220`

**Mechanism.** Three transports are wired as bare pass-through fetches with no AbortSignal and no size cap: the
price feed at src/background/index.ts:191 (`http: (url) => fetch(url)`), the phishing feed at
index.ts:220 (`fetch: (url) => fetch(url)`), and the NFT indexer at src/background/runtime-
rpc.ts:183.

**Impact.** A hostile or compromised third-party host can hang the request indefinitely (no timeout) or make the
MV3 service worker buffer an arbitrarily large body into its heap before any cap applies, evicting
the worker.

**Remediation (shipped).** `src/shared/http-json.ts` is the single bounded reader: one deadline covers
connecting, headers, and every body chunk, and the byte budget is spent AS THE BYTES ARRIVE — the
stream is cancelled the moment it is exceeded. That distinction is the finding, not a detail: a
boundary that buffers a body and measures it afterwards has already paid for the body it was trying to
refuse, which is exactly what Starkscan's `await response.text()` then `text.length > MAX` did. Every
untrusted boundary now goes through it — the price feed, the phishing list, the NFT indexer, Starkscan
(both its success body and the error body it reads back), and the AVNU swap aggregator — each with its
own declared budget in `HTTP_BODY_LIMITS`.

The hardening the reader composes (no cookies, no referrer, redirects refused, and the deadline as an
`AbortSignal`) only reaches the socket if the wiring forwards it, and for three of those five it did
not: the price feed, the phishing list, and the NFT indexer were wired `(url) => fetch(url)`, which
type-checks — TypeScript accepts lower arity — and silently discards all of it. The caller still got
its deadline, because the reader races it wallet-side, so nothing looked broken while the request
stayed in flight forever and a hostile 3xx was followed wherever it pointed (a redirected phishing
feed answering `{"blacklist":[]}` removes protection outright). There is now one shared
`untrustedFetch` in `src/shared/http-json.ts` and every boundary names it, so a wiring site has
nothing left to get right. `tests/conformance/untrusted-fetch-wiring.test.ts` drives the REAL indexer
and phishing feed against a local redirecting server, watches a local server observe the disconnect
when the deadline expires, and scans `src/` for any single-argument `fetch` wrapper — the injected
transport assertions elsewhere are structurally blind to this, which is how it survived a round of
remediation with tests green.

The Starknet JSON-RPC lane is a separate transport and the wallet's largest untrusted boundary — a dapp
can propose its URL through `wallet_addStarknetChain`, and starknet.js reads the body with `.json()`.
A deadline alone is not a bound there: at a modest link speed one 15-second request buffers well over a
hundred megabytes. `timedRpcFetch` reads that body through the same stream-capped reader under the
request's own deadline (`RPC_BODY_LIMIT_BYTES`, 32 MiB — generous over a Sierra class, the largest
legitimate answer) and re-presents it, so `.json()` only ever sees bytes the wallet agreed to hold. The
multisig read lane had defined its own `baseFetch`, which REPLACED a caller's abort signal instead of
composing with it; it now overrides only the NUMBER, and a test walks `src/` to assert no module
outside `provider.ts` builds a provider transport of its own.

The two remaining private readers, in `nft-token-metadata.ts` and `strk20/paymaster.ts`, were checked
rather than assumed: both already cap on the stream, so neither is a defect.

`tests/starknet/http-body-bounds.test.ts` drives each boundary with an endless body and asserts how
much the endpoint managed to emit before it was cut off, which is what distinguishes a streaming cap
from a post-hoc one; `tests/starknet/http-bounded-fetch.test.ts` covers the reader's deadline
behaviour, including a body that stalls mid-stream without ever tripping the size cap.

### MCW-V09-123

- **Severity:** Low  |  **Area:** validation  |  **Status:** Resolved
- **Location:** `src/storage/activity-store.ts:379`

**Mechanism.** csvField (src/storage/activity-store.ts:379-380) quotes a value only when it contains a quote,
comma, or newline — RFC-4180 delimiting, which is not a formula guard: Excel, LibreOffice, and

### MCW-V09-125

- **Severity:** Low  |  **Area:** memory  |  **Status:** Resolved
- **Location:** `src/storage/allowance-store.ts:170`

**Mechanism.** record() reads the whole allowance array, filters out the same id, then keeps
`kept.slice(-(MAX_ENTRIES - 1))` before appending — the slice is taken over the GLOBAL list with no
scoping by accountId or networkId (src/storage/allowance-store.ts:164-172, MAX_ENTRIES = 200 at
:25).

**Impact.** The allowance manager reports a false negative on a security control: an account can show "no
allowances" while holding live unlimited approvals, because its records were pushed out by activity
on a different account.

**Remediation (shipped).** Retention is now two bounds, both in `ALLOWANCE_LIMITS`: 50 entries per
account-and-network scope, and 200 across the whole log — the second because every write goes through
`assertJsonValue`, and a log that outgrows that budget stops tracking new grants silently, which is the
same harm as evicting them.

The scoping is stated rather than inherited. `allowanceScope` names the concept, and the record
validator refuses an entry whose `networkId` disagrees with its account id's `<networkId>:<address>`
prefix — so the same address on mainnet and Sepolia can never share a scope, and that is a checked
property rather than an artefact of how account ids happen to be spelled.

The per-scope cap alone only half-closed the finding, and the second half is the interesting one: with
the log full at four saturated scopes, a globally-oldest eviction lets one busy account push another
account's records out one per write until it reports "no allowances" while still holding live unlimited
approvals — the original false negative, reached at a higher threshold. Recency of WRITE is not evidence
that an allowance is dead, so it may decide which of a scope's own records goes and never which scope
goes hungry. `trimToTotal` therefore levels down the fullest scopes: each round takes a slot from every
scope currently holding the most, leaving the survivors within one entry of an equal share. Levelling
the whole tallest row rather than picking a scope by name is deliberate — a tie broken by a fixed rule
sends every eviction to the same unlucky account until it is empty. A freshly granted allowance is
always retained.

`tests/storage/allowance-store-scope-cap.test.ts` pins both caps against both store implementations,
including that a newly busy account cannot empty an idle one and that the surviving scopes hold
comparable shares; `tests/storage/allowance-store-budget.test.ts` pins that the log stays inside the
storage JSON budget and that the grant just made always survives.

- **Severity:** Low  |  **Area:** vault  |  **Status:** Resolved
- **Location:** `src/wallet/vault-service.ts:158`

**Mechanism.** createLedgerVault refuses to run over a non-fresh store — `if (vault.accounts.length > 0 ||
vault.mnemonic !== null) throw new WalletError("Wallet already exists")` (src/wallet/vault-
service.ts:231-233).

**Impact.** Over a v1-migrated vault the wallet's recovery phrase is permanently set to an unrelated phrase that
restores none of the pre-existing accounts, while the reveal screen presents it as the wallet's
phrase — recovery then depends on the encrypted vault surviving …

**Remediation (shipped).** `createAccount` refuses to displace a stored seed: over a keyless vault it
requires no existing accounts, and over a seeded one it requires the same phrase, so onboarding is
first-run-or-idempotent and `addDerivedAccount` owns every later HD account. Both refusals throw
`Wallet already exists`, matching the `createLedgerVault` sibling.
`tests/wallet/vault-service-create-seed-guard.test.ts` pins the v1-migrated case that motivated the
finding.

### MCW-V09-129

- **Severity:** Low  |  **Area:** consistency  |  **Status:** Open (partially remediated)
- **Location:** `src/starknet/starkscan-wallet.ts:122`

**Mechanism.** defaultRuntimeRpc wires `getTokenBalances: getPreferredBalances` and `getTransactionHistory:
getPreferredHistory` (src/background/runtime-rpc.ts:214,216), built over a hard-coded
https://starkscan.co/v1 client (:192-195) with no preference switch.

**Impact.** Three consequences. (1) Two sources of truth: with an rpcOverride configured, the panel displays
balances and activity from starkscan.co while every transfer, fee estimate, and submission goes to
the override — displayed state and transacted state can diverge …

**Remediation (partial).** The trust ordering is fixed: `createRpcFirstBalances` and
`createRpcFirstHistory` serve from the user's configured Starknet RPC and reach the explorer gateway
only when every configured endpoint has failed, and a gateway failure re-throws the RPC failure so the
third party can never explain away the user's own endpoint. That removes the two-sources-of-truth
divergence and the per-refresh address disclosure.

**What remains.** The disclosure is outage-triggered, not opt-in. A user who configured an RPC override
precisely so no third party sees their addresses still has the account address sent to starkscan.co on
any transient failure of their own endpoint, and has no switch to turn the lane off. Closing this needs
a preferences field, its validator, background wiring, and a settings control — none of which is in
`src/starknet/starkscan-wallet.ts`, where the residual is recorded in the module doc comment so a
reader cannot mistake the current behaviour for a choice the user made.
