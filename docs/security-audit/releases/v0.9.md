## Executive summary

The v0.9 review followed five interacting changes: managed wallet-service routing, encrypted store
upgrades, optional Ledger STRK20 viewing-key custody, a unified public/private Send journey, and
Ledger firmware/application compatibility gates. Review was adversarial and iterative across PRs
[#212](https://github.com/starknet-innovation/mc-wallet/pull/212),
[#214](https://github.com/starknet-innovation/mc-wallet/pull/214),
[#215](https://github.com/starknet-innovation/mc-wallet/pull/215),
[#218](https://github.com/starknet-innovation/mc-wallet/pull/218),
[#221](https://github.com/starknet-innovation/mc-wallet/pull/221),
[#223](https://github.com/starknet-innovation/mc-wallet/pull/223), and
[#225](https://github.com/starknet-innovation/mc-wallet/pull/225). Automated reviewer findings were
treated as hypotheses, reproduced against the final code, fixed where valid, and resolved only
after regression coverage.

No known fund-loss, signing-bypass, cross-account disclosure, or proof-disclosure defect remains
open in the reviewed software scope. Account/network scope is enforced from encrypted persistence
through background operations and UI caches. A private operation binds its route, recipient,
token, amount, pool fee, account, and network before review, then re-checks the mutable chain and
balance facts before proof, signing, and broadcast. A write is considered ambiguous only after an
actual add-transaction fetch may have reached a node.

This record deliberately does not claim that every supported Ledger model and Chrome transport
has been physically exercised. v0.9.0 is required to load the new compatibility path onto target
hardware; the complete USB, HID, Bluetooth, start-state, cancellation, wrong-device, and version
boundary matrix is assigned to v0.9.1 in issue #224.

## Reviewed trust boundaries

- Existing encrypted vault → schema-v4 staging record → verified primary write → staging cleanup.
- Untrusted browser storage → trusted extension-context lockdown → privileged background startup.
- Active account/network mutations → serialized generation authority → scoped stores and UI caches.
- Ledger typed-data derivation ceremony → optional encrypted account-secret record. The ceremony
  itself remains unshipped; this release supplies custody and retrieval boundaries only.
- Side-panel Send fields → pure route resolver → immutable review/preparation → background re-gate
  → Krusty or Ledger signer → one broadcast attempt.
- Privacy SDK proof and paymaster quote → validated relay plan → post-proof submission boundary.
- Starknet RPC endpoint selection and preflight → signed transaction construction → exact
  `starknet_add*Transaction` fetch → determinate or indeterminate outcome.
- Managed Bramble gateway → bounded wallet RPC/STRK20 client → reviewed direct transport fallback.
- Ledger dashboard/application state → OS-version probe → exact-device reconnect → Starknet app
  check → public-key and signature verification.

## Resolved findings

### MCW-V09-001

- **Severity:** Medium
- **Area:** STRK20 relay unlinkability
- **Status:** Resolved

Relay quoting added a public sender approval for the pool fee even though the relay calls
`apply_actions` and recovers its fee through the private fee action. The approval selected a
sender-linking invoke route, created unnecessary on-chain linkage, and could leave allowance
behind. Relayed private batches now contain no sender fee approval. Mixed public/private batches
retain only the exact approval required for an explicit public deposit. Account-mode registration
and deposits retain their required approvals.

### MCW-V09-002

- **Severity:** High
- **Area:** RPC write ambiguity and duplicate submission
- **Status:** Resolved

The shared write boundary originally classified transport-like failures too broadly, including
safe preparation stages and structured rejections. That could retain a maturity guard when no
write occurred or, at the opposite boundary, permit unsafe retry after response loss. Only
`fetchEndpoint` calls for `starknet_addInvokeTransaction`, `starknet_addDeclareTransaction`, and
`starknet_addDeployAccountTransaction` now create an indeterminate write. Endpoint selection,
deployment reads, fee estimation, signing, transaction construction, class decompression, and
preflight failures are determinate. Structured numeric RPC codes remain authoritative even when
adversarial revert text contains transport words.

### MCW-V09-003

- **Severity:** Medium
- **Area:** Vault migration and account/network state
- **Status:** Resolved

The prior vault update path did not provide an authenticated, crash-recoverable staging protocol,
and active account/network mutations were distributed across asynchronous callers. Schema v4
separates optional encrypted account secrets from public account metadata. Migration writes a
validated staging record, verifies it, writes and verifies the primary record, then removes and
verifies removal of staging. A valid current primary wins over stale staging. Invalid staging,
silent write/delete failure, stale sessions, and preference-write failure fail closed. Selection
and account-creation/import mutations share one generation-bound serializer.

### MCW-V09-004

- **Severity:** Medium
- **Area:** Unified public/private Send integrity
- **Status:** Resolved

Early versions of the unified flow rendered some route refusals without enforcing them and could
compose against missing, stale, or cross-scope balances. The final resolver treats absent balances
as unknown rather than zero, requires a configured unlinkable relay for private spending, reads
recipient registration from the pool, and separates pool fees from network fees. The background
binds and re-checks account, network, token, amount, recipient, route, public/private source
balances, and the exact governance-set pool fee before execution. Editing, closing, scope changes,
and a failed final gate invalidate the frozen review.

### MCW-V09-005

- **Severity:** High
- **Area:** Proof and request error disclosure
- **Status:** Resolved

Provider and relay errors may echo submitted parameters. Pattern sanitization removed long blobs
but could not reliably identify the shortest valid proof data or proof facts. Account-mode provider
errors retain only bounded, structured diagnostics after request/proof redaction. Paymaster
`executeTransaction` errors cross a stricter post-proof boundary and always become the stable
generic submission error; no relay-controlled detail reaches the UI. Quote failures occur before a
proof exists and may keep only bounded sanitized diagnostic text.

### MCW-V09-006

- **Severity:** Medium
- **Area:** Ledger compatibility transport
- **Status:** Resolved in software; physical matrix deferred

Reading device firmware requires leaving the Starknet application for the dashboard, which closes
the prior application transport. The original implementation attempted to retain that invalid
transport and parsed only a simplified version response. The final state machine probes dashboard
state, avoids closing an app when already on the dashboard, opens Starknet, reconnects the exact
device, and fails closed when device identity is ambiguous. The OS response parser implements the
length-prefixed MCU field and bounded optional trailing fields, with real-shaped and malformed
fixtures. Key matching and signature verification remain mandatory after compatibility succeeds.

## Release validation

The runtime baseline passed the aggregate repository gate with 2,991 unit/conformance tests and
zero failures, including TypeScript, Biome, file/config, import-layer, dependency-cycle,
extension-manifest, Krusty adapter, multisig class-pin, and privacy SDK checks. The hosted UI Lab
passed 198 deterministic interaction contracts and built its static Storybook. The release
promotion PR is additionally required to pass the enforced 95% coverage floor, high-severity
dependency audit, terminal production build, vendored Krusty/multisig/privacy checks, extension
build, Chromium E2E suite, reproducible package, and SHA-256 verification before merge.

## Residual boundaries

- The managed gateway and its upstream RPC, discovery, proving, and paymaster services remain
  availability and metadata-observation boundaries. No client can hide its configured gateway
  hostname; upstream service addresses and credentials remain server-side.
- Direct RPC fallbacks improve availability but do not provide gateway rate limiting or traffic
  aggregation. Private proof submission still depends on the configured unlinkable relay and
  fails closed when it is absent.
- Optional Ledger viewing-key storage does not define or authorize the future typed-data
  provisioning ceremony. That ceremony still requires a frozen SNIP-12 domain, transform,
  deterministic vectors, and approved UX before it can ship.
- Browser-enforced extension storage isolation and hardware transport APIs remain platform trust
  boundaries. Physical compatibility evidence is not inferred from mocks or dependency support.
- This assurance record is a scoped software review, not an absence-of-defects guarantee or a
  substitute for the planned independent external audit.
