# Item-by-item scope coverage

This ledger follows every bullet in [the scope](v0.10.1-scope.md), in order.
It records source-level assessment, adversarial regression evidence and explicit trust
limits. “Reviewed” means the applicable repository boundary was traced and its relevant
tests inspected/run; it does not mean every line of every dependency was reviewed or that
an external deployment was penetrated. Findings and final gate results are in
[the audit report](v0.10.1-audit.md). No production transactions or credentials were used.

Paths below are repository-relative. `background/` abbreviates
`apps/extension/src/background/`; package names refer to their `src/` trees under
`packages/`. The tests named for each section run in the full repository checks.

## Wallet architecture & trust boundaries

| Scope item | Assessment and evidence |
| --- | --- |
| Client/backend architecture | Reviewed. MV3 background is the custody root; Terminal delegates to the provider and its two serverless handlers retain service credentials. Traced `apps/extension/src/background/index.ts`, `routing/messages.ts`, Terminal `api/` and `wallet/` boundaries. There is no wallet-user database in these handlers. |
| Browser extension/mobile components, if applicable | Reviewed. Manifest, background, side panel, injected provider, isolated content script and Ledger grant page identified. Source inventory finds no Swift/Kotlin, Android manifest, iOS plist or native mobile application; native mobile components are not applicable. |
| RPC/provider dependencies | Reviewed. `platform/starknet` provider/transport/submit and account signer bind writes to the requested chain and check returned hashes. Chain-id agreement cannot authenticate malicious RPC state; external node honesty remains an assumption. |
| External APIs and third-party integrations | Reviewed. RPC, AVNU, token/price/metadata, phishing feed, privacy discovery/prover/paymaster and Nostr are distinct untrusted inputs. Traced parsing, URL selection, response limits and rendering/signing boundaries. SDK pins are checked; remote availability and contract economics are not inferred from local tests. |
| Privileged/backend services and trust assumptions | Reviewed. `routing/senders.ts` enforces extension-page-only privileged messages. Terminal gateway attaches the server key only after route/body policy and uses redirect refusal. V0101-09 narrows that capability. HTTP headers are not client authentication; deployment abuse controls require operator evidence. |

Evidence: `tests/background/routing/key-boundary.test.ts`, `tests/storage/browser-storage*.test.ts`,
Terminal gateway tests, manifest/architecture/import/pin checks, extension E2E.

## Key management & cryptography

| Scope item | Assessment and evidence |
| --- | --- |
| Private key generation, storage and lifecycle | Reviewed. `platform/kms-krusty` adapter validates the pinned WASM boundary and refuses missing crypto. `platform/vault` account derivation and encrypted store retain signing material only in the validated vault. Session clearing evicts derived encryption-key caches. JavaScript strings do not provide assured memory zeroization. |
| Seed phrase / recovery mechanisms | Reviewed. Vault `service/recovery.ts` re-derives selected coordinates, rejects duplicates and commits complete validated snapshots. Imported seeds retain account provenance; recovery discovery stores public candidates/fingerprints, not phrases. KMS owns mnemonic validation. |
| Secure enclave/keychain usage where applicable | Not applicable to software custody: no OS enclave/keychain implementation is present. Ledger is a separate hardware signer; its device/firmware protections and recovery phrase are external assumptions, not properties of browser vault encryption. |
| Key import/export | Reviewed. `accounts/import-inputs.ts`, vault recovery/reveal and UI `settings/reveal-ui.ts` constrain privileged imports and require explicit credential verification to reveal. Imported-key backup copy distinguishes it from a founding phrase. Ledger keys are not exportable through this flow. |
| Encryption of locally stored secrets | Reviewed. `platform/vault/encrypted-store.ts` uses Web Crypto AES-GCM, PBKDF2-SHA256 with bounded parameters, fresh salt/IV, nonextractable keys, authenticated scope/lineage/commit fields and freshness records. Schema/migration tests reject malformed stored data. Browser-local attackers who obtain the encrypted vault can attempt offline password guessing. |
| Signing implementation and cryptographic misuse | Reviewed. Krusty remains the sole software secret-signing implementation; account signature serialization is family-specific. Ledger results are verified against the expected key/hash. V0101-07 fixes late adoption of replacement-session authority during typed/private account resolution. No fallback crypto was added. |
| Prevention of sensitive material leakage through logs, telemetry, backups, etc. | Reviewed. Secret-boundary scan catalog, vault/SDK redaction tests, analytics consent/header construction, public recovery cache, permissioned UI and reveal DOM were checked. V0101-01/02 fix analytics failure/opt-out races. Session credentials intentionally live in trusted-context browser session memory while unlocked; this is not encrypted persistent backup. OS dumps, clipboard history and operator retention are outside repository control. |

Evidence: vault store/cache/schema/migration/recovery/import/reveal tests, KMS adapter tests,
`tests/background/routing/key-boundary.test.ts`, analytics and session regressions,
privacy SDK redaction tests, Ledger queue/signer tests.

## Starknet account & signing logic

| Scope item | Assessment and evidence |
| --- | --- |
| Account abstraction implementation | Reviewed. `platform/starknet/rpc/account-signer.ts` and account-contract modules select OpenZeppelin/Argent/multisig signature formats, deployment metadata and compatible classes. A contract upgrade or compromised deployed implementation remains a chain-level trust change. |
| Account deployment flows | Reviewed. Deployment address/class/key matching, explicit deployment fee review and auto-deployment versus subsequent invoke are separated. Deployment success followed by invoke uncertainty is surfaced without pretending the whole flow failed atomically. |
| Transaction construction and signing | Reviewed. `rpc/rpc-submit.ts`, declare/deployment helpers and background executors carry reviewed calls, resource bounds and account context to the signer. V0101-06/07 retain claim-time authority through deferred execution. |
| Nonce handling and replay protection | Reviewed. Starknet transaction hashes include SDK-supplied nonce/version/chain/account context. Multisig intent execution rechecks current nonce/configuration against the frozen intent. CallSet/outside-execution have distinct protocol rules; their replay resistance also depends on pool/account contract enforcement. |
| Chain ID / network validation | Reviewed. Provider chain probes and approval account/network/chain bindings refuse changed execution context. Multisig, deployment and declare select the stored network. Arbitrary typed-message domains are presented as message content; they are not a transaction network switch or a universal replay-prevention guarantee. |
| Typed-data signing / SNIP-12 flows | Reviewed. Typed-data grammar, graph, revision, scalar/container validation and digest construction; UI classification exposes supported message structure and denies unclassified requests. Typed-data authorization races are covered by V0101-07. |
| Signature validation assumptions | Reviewed. Ledger verifies device signatures against the expected public key/hash; Krusty return shape and signer identity are validated. Starknet account contracts determine signature acceptance. Device firmware and independent cryptographic correctness are not established by mocks. |
| Fee estimation and transaction simulation | Reviewed. Fee echo, per-component deployment/invoke ceilings, affordability and stale-estimate checks; privacy simulations strip submit-capable proof material. Estimates depend on untrusted/current chain state and do not guarantee future execution success. |
| Multicall/batched transaction handling | Reviewed. Frozen approval payload digests, bounded calls/calldata, self-call and recipient policies, multisig prepared-hash comparison and privacy call/proof binding. V0101-08 now checks both embedded private executor calls and rejects additional calls; V0101-10 disables planning without a reviewed executor pin. |

Evidence: Starknet transaction/deployment/declare/fee suites, typed-data conformance/injectivity/
graph tests, multisig intent/signature suites, privacy CallSet golden vectors and proof gates,
new approval/session and private-route regressions.

## Transaction security

| Scope item | Assessment and evidence |
| --- | --- |
| Verification of transaction destination, calldata and value | Reviewed. Background transfer/invoke/swap policies and approval digests bind review to execution. Public AVNU binds router and trade intent. V0101-08 extends intent checks to private executor calldata; planning is disabled until an independent executor deployment is reviewed/pinned (V0101-10). |
| User confirmation screens vs. actually signed payload | Reviewed. Fee echoes and private payload digests prevent silent substitution; supported typed-data fields are decoded for review. Private swap now displays the actual decoded minimum received, with one slippage constant shared by server and UI; that route remains unavailable until executor verification is complete. |
| Transaction tampering | Reviewed. Approval claims are consumed once; context and digest are revalidated. V0101-06 prevents a claimed request from crossing lock/unlock even while queued inside the coordinator. Regression tests confirm no mutation after rejection. |
| Malicious calldata / deceptive transaction scenarios | Reviewed. Felt/size limits, self-call refusal, poisoned-recipient checks, allowance/NFT ambiguity guards and unknown-call review. Private route tests mutate targets, selectors, approval amounts, beneficiary, fees, spans and minimums. User consent to an unknown contract is not proof the contract is safe. |
| Approval and token-transfer flows | Reviewed. Exact transfer fields and approved allowance amounts, allowance owner scoping, token/NFT ambiguity refusals and tracking of submitted approvals. Private executor permits exactly the reviewed token approval and AVNU exchange call. |
| Contract deployment / upgrade interactions | Reviewed. Known class compatibility, declaration class-hash recomputation and reviewed deployment fees; multisig configuration changes invalidate old intents. Account self-upgrade calls cannot masquerade as ordinary recipient calls. Independent deployed-contract/upgrade-admin assurance remains external. |
| Signing of arbitrary messages and potentially dangerous signatures | Reviewed. No dapp raw-hash signing message; SNIP-12 requires per-request review. Outside-execution paymaster messages are reconstructed from exact calls and bounded validity fields. The UI warning now explicitly states that signatures can authorize transfers or account access. |

Evidence: approval-security and fee-queue tests, transaction/recipient/allowance suites,
Terminal public/private AVNU intent tests, sign-request rendering/conformance tests,
privacy paymaster typed-data tests and packaged approval journeys.

## DApp / Wallet connectivity

| Scope item | Assessment and evidence |
| --- | --- |
| Wallet connection and permission model | Reviewed. Account grants are origin-scoped and expose the active granted account; new connections require approval. Non-secret discovery methods have deliberately narrower/public capabilities. |
| Origin/domain validation | Reviewed. Page event source and origin, browser runtime sender id/origin/URL consistency and normalized origins are checked. Claimed request text is not accepted as browser sender evidence. |
| DApp authorization lifecycle | Reviewed. Connect/reconnect, stored grants, approval-time re-resolution, blocklist rechecks and revocation events. Revocation refuses subsequent grants; an already-broadcast transaction cannot be revoked by disconnecting a site. |
| Cross-origin messaging | Reviewed. Content bridge posts responses to the exact origin; request validation and request correlation precede runtime forwarding. Public inpage JavaScript has no custody capability on its own. |
| Malicious website scenarios | Reviewed. Spoofed sender/origin, privileged message attempts, blocked origins, oversized/flooded requests, malformed payloads and NFT HTML isolation are covered by source guards and regression/browser tests. |
| Permission escalation between connected applications | Reviewed. Message allowlist is enforced-derived from provider sources; privileges are denied by default. Private subaccounts bind to origin; an approval for one site does not grant another site a signing capability. |
| Account/network switching | Reviewed. Active-state coordinator and cross-store mutations bind account/network preferences and vault state; approval context must still match. Failed mutations lock their own generation. V0101-06 holds claim authority through coordinator waits. |
| Session persistence and revocation | Reviewed. Trusted-context memory mirror, bounded lifetime, verified erase/revocation marker, restore generation and signer invalidation. V0101-03/04/06/07 close restore, metadata and deferred execution races. |

Evidence: sender/key-boundary tests, origin/grant/reconnect tests, provider bridge tests,
subaccount-origin-binding tests, session/lock/restore/active-state tests and dapp E2E.

## Authentication & session management

| Scope item | Assessment and evidence |
| --- | --- |
| Wallet unlock mechanisms | Reviewed. Privileged unlock validates the explicit credential through vault decryption and reconciles stored account/network state before publishing an unlocked session. |
| Password/PIN controls | Reviewed. Software vault passphrases have a 12-character minimum and bounded maximum. No separate browser-wallet PIN authentication path was identified. Ledger PIN enforcement belongs to the device. |
| Brute-force protections | Reviewed with explicit limitation. Sender gating prevents websites from invoking unlock; the KDF increases guessing cost. There is no durable online attempt lockout, and a client counter would not prevent guessing a copied encrypted vault. Password quality remains essential. |
| Session timeout/locking | Reviewed. Passive dapp polling does not renew the session; explicit user work may renew within policy. Alarms and lazy expiry revoke authority and clear key caches/mirror state. |
| Authentication bypass | Reviewed. Privileged sender checks plus successful decryption protect unlock/reveal; generation checks protect asynchronous work. Replacement-unlock bypasses found during this audit are fixed and regression tested. |
| Device/session management if a backend account exists | Not applicable to wallet-user accounts: no backend login/device-session database was found. Ledger transport ownership, broker channel, request ids, timeout and signature settlement are separately reviewed; service API credentials belong to deployment operators. |
| Recovery/account takeover scenarios | Reviewed. Recovery requires the phrase/key rather than a remote account reset; atomic import/restore and provenance checks avoid mixed accounts. A stolen recovery phrase or compromised unlocked browser/OS remains sufficient for takeover and is not mitigated by an app password reset. |

Evidence: unlock/session/mirror/restore suites, vault recovery and migration suites,
Ledger broker/grant/queue tests and newly added lock/replacement regressions.

## Authorization & API security

| Scope item | Assessment and evidence |
| --- | --- |
| IDOR/BOLA/BFLA | Reviewed where applicable. Background object access is bound to origin/account/context; no per-user server data store or object ids requiring backend user authorization were found. Server function capability abuse is applicable and V0101-09 fixes a permissive transaction envelope. |
| Privilege escalation | Reviewed. Extension messages use browser sender authority, and gateway routes/body policy constrain the server credential. V0101-09 rejects extra invoke legs, alternate transaction types and alternate pool selectors before fetch. |
| Authentication bypass | Reviewed with deployment limitation. Terminal origin checks and extension Fetch Metadata distinguish browser traffic, not authenticated clients. An external HTTP client can spoof headers. These APIs must not be treated as confidential authenticated endpoints. |
| API token/session handling | Reviewed. Paymaster key is server-only, added only on its upstream route, never returned or logged by the handler. Redirects are refused and upstream errors sanitized. Scope/rotation of the deployed key requires operator evidence. |
| Rate limiting | Reviewed. Extension admission/queue/payload limits and transport timeouts bound individual work. Gateway sizes/timeouts are bounded, but durable server abuse/rate limits are an explicit deployment prerequisite; no live firewall configuration was supplied or verified. |
| Input validation | Reviewed. Exact methods/routes, origin shape, bounded JSON/proof/calldata, chain/pool/fee-token checks and client response validation. Gateway union/selector gaps and private-route semantic gaps were reproduced and fixed. |
| Business-logic abuse | Reviewed. Duplicate approval execution, stale authority, hidden private executor calls, weakened trade minimum and expanded paymaster capability were exercised. External executor economics and service-side accounting are not proven by client code; V0101-10 contains the unverified executor path by disabling planning. |
| Sensitive information exposure | Reviewed. Server errors omit upstream details; request bodies are not logged. Wallet secrets remain behind the vault/key-boundary catalog; viewing keys are absent from provider messages. Analytics consent races and stale account metadata were fixed. Operator logs/backups require external evidence. |

Evidence: gateway origin/size/capability tests, private-swap client/intent tests,
background key-boundary and approval security suites, privacy SDK redaction tests.
The pinned SDK's `dist/index.mjs` was inspected for the actual paymaster wire envelope
and Cairo-1 executor serialization, rather than inferring those formats from field names.

## Client-side security

| Scope item | Assessment and evidence |
| --- | --- |
| XSS / HTML injection | Reviewed. String-HTML sink inventory traces dynamic values through escaped rendering; Terminal uses React text rendering and no dangerous HTML sink was found in its source scan. NFT HTML is isolated rather than interpolated into the wallet. |
| DOM-based attacks | Reviewed. Swap/token/approval summaries, data attributes and error rendering use escaping/textContent; sign-request structured views fail closed on unclassified data. No production eval/new Function/document.write was found in the inspected source inventory. |
| Extension message-passing security | Reviewed. Background validates message type, allowed fields, sender and capability; only public provider code is web-accessible. Secret-path catalog is checked against handled wallet message types. |
| Content-script isolation | Reviewed. Isolated content bridge has no vault access; trusted-context storage access levels are required before privileged startup. Page code can imitate provider UI/API objects but cannot acquire extension-page sender authority. |
| CSP and browser security controls | Reviewed. MV3 packaged scripts, WASM-only eval exception, narrow public resource, explicit/optional hosts and separate opaque NFT sandboxes. Browser tests exercise script isolation and no-egress sandbox behavior. CSP is defense in depth, not a replacement for safe HTML. |
| Deep-link / custom URL handling for mobile | Not applicable: no native mobile/custom-protocol registration was identified. Web/service URL validators and browser host permissions are applicable and reviewed; they do not grant arbitrary local-file access. |
| Clipboard-related risks | Reviewed. Copy actions are user initiated, text-only and fail visibly; recovery phrase paste is bounded through input validation. Revealed secrets are shown after reauthentication and are not automatically copied. OS clipboard managers and manual copying cannot be revoked by the wallet. |
| Local storage / IndexedDB exposure | Reviewed. Extension persistence goes through browser adapters and permissioned stores; raw storage is not a UI custody API. Encrypted vault is persistent, unlock mirror is browser session memory restricted to trusted contexts. Terminal browser persistence holds dapp state rather than custody keys. Malicious extension pages or OS access remain outside this isolation model. |

Evidence: storage access-level tests, key-boundary/conformance scans, UI rendering/sign-request
tests, `tests/sandbox/sandbox-render-payload.test.ts`, and packaged NFT sandbox E2E.

## Closure and residual evidence

All 59 scope bullets have an assessment above. The repository portion includes source
tracing, confirmed fixes and automated validation; native-only items are explicitly not
applicable. This does not close the external evidence requirements: deployed firewall/rate
policies, key scope/rotation, analytics retention, physical Ledger behavior, independent
upstream cryptographic review and deployed pool/executor/upgrade authority assurance.
Those require the relevant operator/device/contracts, not invented local test results.
