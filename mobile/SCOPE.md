# Bramble Mobile — Scope

Status: prototype on `feature/mobile-wallet` (2026-09-24). iOS builds and passes its unit and
mainnet UI suites on the simulator. Android compiles and passes its JVM and instrumented suites
on an API 35 emulator (2026-09-25); its CI job has not run on GitHub yet.

## Goal

Ship Bramble on iOS and Android with the same key custody, vault format, network catalog, and
design system as the browser extension, using **Krusty KMS in Rust** as the shared middleware
instead of its WASM build. Native UI per platform (SwiftUI, Jetpack Compose); one Rust core.

## Architecture

```
            SwiftUI app                         Compose app
   (screens, URLSession, Keychain/SE)   (screens, HttpsURLConnection, Keystore)
                 │  UniFFI (Swift)                    │  UniFFI (Kotlin/JNA)
                 └───────────────┬────────────────────┘
                        bramble-core  (mobile/core, Rust)
     kms.rs      → wallet-core (shared Rust core, pinned by rev until 2.6's tag) → krusty-kms =2.0.0, which mobile never names; the extension's krusty-kms-wasm stays on 0.11
     vault.rs    → wallet-core's EncryptedEnvelope v3, byte-compatible with the extension; the passphrase rule stays here
     wallet.rs   → WalletCore: lifecycle + key custody; phrase never crosses FFI except backup/reveal
     networks.rs → generated/{networks,token-registry}.json  (rendered from wallet-model/networks), as wallet-core's catalog records
     portfolio/  → wallet-core's portfolio (prices, tokens, token reads, saved balances); the FFI objects and Bramble's copy stay here
     history/, activity/ → wallet-core's history and activity log; the FFI objects, the file lock, deletion and Bramble's copy stay here
     privacy/    → wallet-core's privacy reads (the read plan, gates, Home rows); the FFI object, its PrivacyHost over the session, the routing loader and override stay here
     send/       → wallet-core's sans-IO JSON-RPC and send Plan: core builds requests and judges responses; host moves bytes
     recovery_scan.rs → wallet-core's account addresses and sans-IO discovery scan; Bramble's catalog, rules and wording stay here
     argent_multisig.rs, multisig_rpc.rs, class_declared.rs → wallet-core's multisig account and reads, on Bramble's pinned class; the registry file stays here
     nostr_relay.rs, coordination.rs → wallet-core's relay grammar, judges and sync window, read one page per relay until 2.7; the wss-only rule, the coordination file and the trust judgement stay here
```

## Security posture (implemented)

- **Keys stay in Rust.** Private keys are derived per call into the zeroizing `SecretFelt`
  and never returned. The phrase is held in a zeroize-on-drop payload for the unlocked session
  only; it crosses FFI only at creation (to back it up) and on a password-rechecked reveal.
- **Fail closed.** No fallback crypto; every Krusty output is re-validated (curve-order range,
  non-zero felts); errors carry an operation name, never input text.
- **Vault at rest.** PBKDF2-SHA-256 600k → AES-256-GCM, additional data binds scope, lineage and
  commit; tampered iteration counts are refused. Atomic write-then-rename. iOS: Application
  Support, `FileProtectionType.complete`, excluded from backup. Android: `noBackupFilesDir`,
  `allowBackup=false`, data-extraction rules exclude every domain.
- **Vault v2 and biometrics** ([docs/vault-security.md](docs/vault-security.md)). A random DEK seals
  the payload; the passphrase slot is the extension envelope around it, and an optional biometric
  slot wraps it under a host-generated 32-byte secret W held behind `.biometryCurrentSet`
  (iOS Keychain) / a biometric-bound Keystore key (Android). W is the one new FFI crossing, host →
  core only; the DEK never leaves Rust. v1 vaults migrate on the first passphrase unlock.
- **Backoff and idle lock in the core.** Four free wrong passphrases, then 30 s doubling to 1 h,
  persisted in `security.json`, counted before the KDF under one attempt mutex, and measured on a
  monotonic, boot-scoped host clock (no wall clock). The 30-minute idle lock is generated from the
  extension's `DEFAULT_TTL_MS` and renewed only by user-initiated operations.
- **Session.** Leaving the foreground locks and zeroizes (iOS `scenePhase`, Android
  `ProcessLifecycleOwner`). iOS covers the app-switcher snapshot; Android sets `FLAG_SECURE` and
  disables the recents screenshot.
- **Phrase display.** Masked while the iOS screen is recorded/mirrored, hosted in the secure layer
  screenshots omit (fails closed), screenshot warning; third-party keyboards blocked on iOS; no
  autocorrect, capitalisation, content type or keyboard learning on phrase/password fields
  (Android: one `SecretField` in `design/SecretField.kt`, a platform `EditText` with a
  `TYPE_CLASS_TEXT` password variation, `TYPE_TEXT_FLAG_NO_SUGGESTIONS`,
  `IME_FLAG_NO_PERSONALIZED_LEARNING`, autofill excluded, no copy/cut/share, and no saved-instance
  state, covered by `SecretFieldTest`); the clipboard is cleared after a phrase paste on both
  platforms.
- **Network.** Sans-IO: no TLS or HTTP code in Rust. HTTPS only (ATS / `usesCleartextTraffic=false`),
  ephemeral URLSession. An endpoint is trusted only after `starknet_chainId` proves the chain;
  responses must answer their request id, are size-bounded, and u256 limbs are range-checked.
- **STRK20 viewing key (owner-approved exemption, 2026-09-24).** The one secret-derived value that
  leaves the core: the scoped viewing key may travel inside the discovery request body the
  Swift/Kotlin host carries, in a buffer the host wipes after the exchange, over HTTPS only, to the
  configured discovery service only (never an OHTTP network, which is not routed). It is never
  persisted, logged or shown, no exported type holds it alone, and this matches what the
  extension sends. Terms and enforcement: [docs/privacy.md](docs/privacy.md) §1.1.
- **Clipboard.** Public identifiers only (account address, signer public key, class hash; see
  `docs/accounts.md` §2.8), local-only and expiring after two minutes on iOS; Android clears its
  own clip after two minutes. Never the phrase, a private key, or a viewing key.
- **Supply chain.** Every Rust dependency pinned exactly with a committed `Cargo.lock`; builds use
  `--locked`. Gradle and Android dependencies pinned exactly.

## Phases

State of `feature/mobile-wallet` after merging vault-security, android-parity, design-mobile,
transactions, accounts, nostr-multisig, portfolio-activity and privacy. iOS is built and was
verified on each branch. Android was first compiled and run on 2026-09-25 (branch
`mobile/todo-android`): `:app:assembleDebug` builds, 38 JVM unit tests and 36 instrumented tests
pass on an API 35 emulator (the opt-in `LiveMainnetWalletTest` is skipped), and ktlint/detekt are
clean. The per-workstream docs under `docs/` record their Android parts as written before that
first build.

**Phase 0 — prototype (done).** Create/import, backup, unlock/lock, mainnet/Sepolia, receive with
QR, explorer, reveal phrase, delete wallet. Android matches the iOS screens one for one with
FLAG_SECURE, overlay and autofill hardening, secret fields without suggestions, and lock on
background (including a lock that lands mid-PBKDF2).

**Phase 0.1 — iOS design parity (done, presentation only).** Generated elevation, press,
breakpoint and per-component metrics read from the extension's side-panel stylesheet; Dynamic
Type, 44pt hit targets, haptics, reduced motion, edge swipe-back, sheet detents; shared callout /
empty / error / pill / toast / skeleton components; flat input fields (no edge, stroke or shadow,
enforced by `tests/conformance/mobile-design-system.test.ts`); a Debug-only offline RPC fixture
transport. Every merged feature's screens use these components and metrics, and success toasts
go through `store.notify`. Still open: SE / Pro Max device runs, large Dynamic Type and Reduce
Motion snapshot passes.

**Phase 0.5 — account parity (done; `docs/accounts.md`).** Vault v3 with typed account records,
one active account, labels and groups, and one migration chain v1 → v2 → v3; sans-IO "Find your
accounts" discovery for Bramble (OpenZeppelin), Ready (Argent) and Braavos; the
drawer's Add account ("Regular account", and "Multisig account" into the Ready Multisig
gateway). Everything that acts for an account names its record id: signing, transfer and
deployment plans, activity, shared-account signers, and private-balance reads
(`sign_hash(index)` is removed and `tests/ffi_surface.rs` forbids index-based signing or planning
exports). Ready accounts send and deploy with the extension's `argent-signer-array`
authorization (`docs/accounts.md` §2.7a). Not yet: private-key import and Braavos signing.

**Phase 1 — sendable wallet.**
1. Android build and tests: NDK build via `build-core-android.sh`, `:app:assembleDebug`, the JVM

   core's `prepareDeployment` plan), the Activity list over the core's one activity

   `TransferPlan` bound to the session generation (`lock_epoch`), automatic OZ deployment, a
   standalone Deploy flow, and the extension's review, fixture-checked against the extension.
3. Biometric unlock, persisted back-off and idle lock — **done** (`docs/vault-security.md`;
   decisions D1–D6 open there).
4. CI job for `cargo test --locked`, clippy, `cargo deny`, and the iOS unit suite. **Open.**

## Decisions to make

- **Vault portability.** Mobile uses the extension's envelope but its own payload
  (`bramble.mobile.vault.v1`). Should phase 2 adopt the extension's vault schema v4 so an
  encrypted export moves between devices?
- **UniFFI (Mozilla) as a new dependency.** It generates both bindings from one Rust surface and
  removes hand-written `unsafe` FFI. The alternative is a hand-written C ABI like Krusty's
  `crates/ffi-mobile`.
- **Upstream vs. local core.** Krusty's `feat/mobile-pq-signer` branch deliberately keeps its
  mobile ABI public-material-only. A software-key wallet core belongs here, not in that crate —
  confirm with the Krusty maintainers.
- **Minimum OS.** iOS 17 (for `@Observable`) and Android 9 / API 28 are assumed.

## Known limits

- Swift/Kotlin `String` passwords and the phrase shown at backup can't be zeroized by the host.
  The Rust side zeroizes its copies, but serde's parse buffers aren't guaranteed to be wiped.
- The biometric wrap secret W is zeroed in the host's own buffer and in the core's
  `Zeroizing` copy, but not in the Keychain's immutable reply `CFData` / `javax.crypto`'s internal
  buffers, nor in UniFFI's lowering buffers (the foreign-side serialisation array and the `RustBuffer` the
  core lifts `Vec<u8>` from are freed unwiped). UniFFI has no hook for this; the fix is upstream
  UniFFI or a dedicated pointer-and-length FFI entry for W.
- iOS still shows the system Passwords bar on secure fields; there is no public API to remove it
  without a misleading content type.
- A created wallet's vault is written before its backup is confirmed (iOS and Android). If the
  app locks during Save phrase or Confirm backup, nothing prompts the user to finish the backup
  after unlock; Reveal secrets is the way back. The extension verifies words before creating.
- The STRK20 viewing key reaches host memory inside each discovery request body; hosts wipe their
  buffer after the send, but HTTP/TLS internals cannot be wiped (docs/privacy.md §1.1, §5). This is
  the owner-approved exemption under Security posture.
- Send (ERC-20 from an OpenZeppelin account, with automatic deployment) is implemented on iOS
  and Android; Android's Send screens compile but have no instrumented send-flow test yet (the
  deployment plan they share is covered by `DeployFlowTest`). See docs/transactions.md.
- Android has token detail but not yet the token management screens (add by contract, find held
  tokens, hide/show) that iOS has.
