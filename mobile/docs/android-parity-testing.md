# Android parity: fixtures and test plan

Sections 7 and 8 of [android-parity.md](android-parity.md), kept in their own file so each stays
under the repository's 500-line limit. Section numbers match the design document.

## 7. Parity fixtures

Android adds no new cross-language fixture of its own. It relies on the existing ones and checks them
from Kotlin:
- `mobile/core/tests/fixtures/extension-parity.json`: addresses, public keys and signatures, plus the
  `ui` block (strength bands, avatars, word assist, backup verify). It is regenerated by
  `bun run mobile:parity` and re-checked by `tests/conformance/mobile-generated.test.ts`.
- `BrambleTokens.generated.kt` and the drawables are byte-compared by the same conformance test
  (and so are the Android token logos, section 4.2).
- New and Android-local: `app/src/test/resources/qr-parity.txt`, written by the Bun script
  `mobile/android/scripts/qr-fixture.ts`, which runs the extension's `shared/qr.ts` over five
  inputs (the E2E address, a 66-char address, both sides of the version-1 capacity, and a
  198-byte string that needs version 10 and its 16-bit length). A line format rather than JSON, so
  the JVM unit test needs no parser (`org.json` is a stub off-device). `QrCodeTest` asserts the
  Kotlin matrices are identical. The fixture is regenerated, not hand-edited. A conformance check
  that it is fresh would need a `tests/` change, so it is flagged for the orchestrator.

## 8. Test plan

Toolchain: the Android code was written on a machine without a JDK or Android SDK, and was first
compiled and run on 2026-09-25: `:app:assembleDebug` builds, and the JVM and instrumented suites
pass on an API 35 emulator (counts in `mobile/README.md`). To run it, install: JDK 17; Android SDK platform 35 + build-tools 35 + an API 35 emulator image; NDK
r27+ with `ANDROID_NDK_HOME`; `rustup target add aarch64-linux-android x86_64-linux-android`;
`cargo install cargo-ndk --version 4.1.2 --locked`.

Then run `mobile/scripts/build-core-android.sh debug`, and in `mobile/android` run
`./gradlew :app:testDebugUnitTest :app:connectedDebugAndroidTest` on an emulator.

### 8.1 Gradle wrapper (pinned)

The wrapper is Gradle 8.11.1, which works with AGP 8.7.3 and Kotlin 2.1.0.
- `gradle/wrapper/gradle-wrapper.properties` sets `distributionUrl=
  https://services.gradle.org/distributions/gradle-8.11.1-bin.zip` and pins `distributionSha256Sum`
  to the value published at `…/gradle-8.11.1-bin.zip.sha256`.
- `gradlew`, `gradlew.bat` and `gradle-wrapper.jar` come from the `v8.11.1` tag of `gradle/gradle`.
  The jar is checked against `…/gradle-8.11.1-wrapper.jar.sha256` before it is committed, since a
  wrapper cannot be generated without a JDK.
- CI would add `gradle/actions/wrapper-validation` if an Android job is ever added. That is out of
  scope here.
- Done: the three files were fetched from the `v8.11.1` tag, the jar's SHA-256
  (`2db75c40…448046`) matched the published `gradle-8.11.1-wrapper.jar.sha256`, and
  `distributionSha256Sum` is `f397b287…eee151c6`.
- Standards gate: `.jar` is not in `BINARY_EXTENSIONS`, so the jar is read as UTF-8 and
  line-counted. It has 152 newline bytes, well under the 500-line limit, and the other per-file
  rules apply only to `.ts`, so the gate passes without the flagged one-token change. It is left
  as an optional cleanup (section 9).

### 8.2 Dependencies (test only, exact pins, reason for each)

- `androidx.compose.ui:ui-test-junit4` and `ui-test-manifest` (debug) through the existing BOM
  2024.12.01: Compose finders and actions for Compose UI.
- `androidx.test:runner:1.6.2` and `androidx.test.ext:junit:1.2.1`: the runner, JUnit4 rules and
  `ActivityScenario`.
- `androidx.test.espresso:espresso-core:3.6.1`: secret fields are platform `EditText`s inside
  `AndroidView`, not Compose semantics nodes, so Compose's `performTextInput` cannot reach them.
  Tests scroll the field's Compose wrapper into view by its test tag (`secret:<label>`), then type
  with `onView(withContentDescription(label)).perform(replaceText(…))`.
- `androidx.test:orchestrator:1.5.1` (`androidTestUtil`): runs each test in its own instrumentation
  with `clearPackageData=true`, so every test starts in a fresh process with no vault and default
  preferences (section 8.4).
- `junit:junit:4.13.2`: JVM unit tests.

Each version is the one released together in the androidx.test 1.6 set and was checked to exist on
Google Maven / Maven Central. No new production dependency.
`testInstrumentationRunner = "androidx.test.runner.AndroidJUnitRunner"`,
`testOptions.execution = "ANDROIDX_TEST_ORCHESTRATOR"`, `animationsDisabled = true`.

### 8.3 JVM unit tests (`app/src/test`, no device)

`ErrorTextTest` (every `CoreError` → iOS string), `AddressTextTest` (now instrumented: it calls the
core's `accountLabel`, which the host JVM cannot load),
`QrCodeTest` (matches `qr-parity.txt`), `BackupVerifyTest` (positions, trim, case, empty, short
phrase), `WeakAckStateTest` (tick cleared when the acknowledgement stops applying, kept while it
applies), `RecoveryEntryTest` (lowercase, space-advance, paste spread, growth to 24),
`SessionGuardTest` (a lock invalidates earlier tickets), `ClipboardPolicyTest`,
`RpcClientBoundTest` (64 KiB cap), and
- `SourceHygieneTest`: checks on every app source for colour and dp/sp literals outside `design/`,
  logging, `SecureOff`/`Popup`/`clearFlags`, and `rememberSaveable`.

### 8.4 Instrumented tests (`app/src/androidTest`, mirroring iOS)

Both flow tests run on an emulator, never on a physical device with a real wallet. Test state is
reset by Android Test Orchestrator with `clearPackageData=true`, the equivalent of iOS's "uninstall
first": each test starts in a fresh process, so `BrambleApplication.onCreate` builds the
`WalletStore` over no vault and default preferences, and the network is the default, mainnet. There
is no `pm clear` (it would kill the instrumented process) and no network argument (production code
takes no test input). After "Open Bramble" the home screen reads public balances from mainnet RPC,
as the iOS suite does; no assertion depends on them and nothing is ever sent.

`OnboardingFlowTest.createBackupAndConfirm` mirrors `testCreateBackupAndConfirm` step for step:
"Create a new wallet" → "ui test passphrase" twice → Continue → tick mainnet ack → "Add selected
account" → assert "I saved my phrase" disabled → "Show recovery phrase" → read test tags
`recovery-word-1..12` → words 3/7/11 into "Word 3/7/11" → "Backup confirmed." → Continue →
"You’re all set" → "Open Bramble" → "Account 1" → clean up via Settings → "Remove wallet from this
device" → passphrase → "Remove wallet" → "Create a new wallet" is back. Buttons are found by visible
text plus a click action (so the "Remove wallet" title never matches), icon controls by content
description, secret fields as above.

`OnboardingFlowTest.importMainnetThenLockUnlock` mirrors the iOS import test: public E2E
phrase one word per "Word N" → "Find your accounts" → Review shows the short form of
`0x208361e3…398d9` → add → Receive ("Copy address") → Back → Settings → Network → Back →
Appearance → Light → Dark → Back → Accounts ("Add account", short address) → Close → "Lock wallet" →
"Welcome back" → wrong passphrase shows "Incorrect passphrase" → unlock → "Account 1".

Its opt-in live variant, `LiveMainnetWalletTest`, reads `BRAMBLE_MOBILE_MAINNET_MNEMONIC` /
`_ADDRESS` from `InstrumentationRegistry.getArguments()`. It is skipped with `assumeTrue` when they
are absent, and refused when the argument `ci=true` is present (`build.gradle.kts` sets it from
the host's `CI` variable). It never broadcasts, never prints the phrase, and saves no screenshots; its header warns that instrumentation arguments reach the Gradle command line and that
an Espresso failure dumps the view tree, so results are deleted after a real run.

`CoreBridgeTest` mirrors `CoreBridgeTests.swift`: fixture addresses, public keys and signatures
(`extension-parity.json` copied into `androidTest/assets` by a Gradle `Copy` task, not committed); a
locked core refuses `sign_hash`; a wrong password raises `WrongPassword`; Sepolia's chain id
`0x534e5f5345504f4c4941` includes STRK.

Security: `SecurityTest` (FLAG_SECURE, vault path, autofill exclusion, obscured touches, backup
off), `SecretFieldTest` (full `inputType` with class bits, `imeOptions`, autofill, no saved state),
`LockOnBackgroundTest` (Home locks; a lock during unlock, reveal or create wins; mid-onboarding
lands on unlock with the phrase recoverable through Reveal; before a vault exists, backgrounding
drops the typed phrase and restarts at welcome), `ReceiveTest` (clipboard holds exactly
the address).

Test screenshots (`captureToImage`) are saved best-effort for design review, like the iOS
`snapshot` calls, under the app's `additional_test_output` media directory, except in the live mainnet test, which saves none.

### 8.5 Other suites

- Rust: no core change; `cargo test --locked` and `cargo clippy --all-targets --locked` stay green.
- Swift unit tests and XCUITest on the "Bramble android-parity" simulator: iOS is unchanged in this
  workstream. As a regression guard they run there after `mobile/scripts/build-core-ios.sh debug`
  and `xcodegen generate`, to prove the shared-script change (section 4.2) did not disturb iOS
  assets. Never on "iPhone 16".
- `bun run mobile:assets` (only the new Android token-logo files appear), `bun run mobile:parity`
  (no change) and `bun run check` must pass.
